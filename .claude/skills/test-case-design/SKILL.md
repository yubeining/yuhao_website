# 测试用例设计

从需求文档、技术方案或一段改动中提取测试点，生成结构化用例矩阵。

输入：`$ARGUMENTS`（文档路径 / 模块路径 / "当前 diff"）

## Phase 1 — 提取测试点

| 来源章节 | 提取什么 | 得到的测试类型 |
|---|---|---|
| 接口定义 | 每个接口的参数 / 响应 / 错误码 | 功能 + 参数校验 + 权限 |
| 业务规则 | 规则与约束条件 | 边界 + 正向 / 反向 |
| 数据模型 | 字段约束（非空 / 唯一 / 枚举 / 长度） | 数据验证 |
| 状态机 | 状态转换路径 | 状态流转 + 非法转换 |
| 异常处理 | 异常分类与策略 | 异常路径 |
| 外部依赖 | 第三方调用 | 容错 + 降级 + 超时 |
| 安全 | 权限 / 注入 / 敏感信息 | 安全 |

没有文档、只有代码时：从公开函数签名 + 分支 + 早返回条件反推测试点。

## Phase 2 — 生成用例矩阵

按模块分组，每条用例信息完整：

```markdown
## 测试用例 — <模块名>

### <接口 / 函数>：POST /api/orders — 创建订单

| # | 用例名称 | 前置条件 | 操作 | 预期结果 | 优先级 | 类型 |
|---|---|---|---|---|---|---|
| 1 | 正常创建 | 已登录，有库存 | 提交有效参数 | 201 + 返回订单号 | P0 | 功能 |
| 2 | 商品 ID 为空 | 已登录 | productId=null | 400 INVALID_INPUT | P0 | 参数校验 |
| 3 | 库存不足 | 库存=0 | quantity=1 | 409 OUT_OF_STOCK | P0 | 异常 |
| 4 | 5 秒内重复提交 | 刚提交过同单 | 重复提交相同参数 | 幂等返回已有订单 | P1 | 边界 |
| 5 | 未登录访问 | 无凭证 | 提交有效参数 | 401 | P0 | 安全 |
```

类型枚举：`功能` / `参数校验` / `边界` / `异常` / `安全` / `性能` / `兼容`
优先级：`P0` 主流程与安全 / `P1` 重要分支 / `P2` 锦上添花

**命名统一用** `should_<预期>_when_<条件>`，便于与实际测试方法名对齐核查。

## Phase 3 — 覆盖门禁

<HARD-GATE>
最低覆盖要求，不达标禁止收尾：

- 每个接口 / 公开函数至少：1 正常 + 1 参数校验 + 1 异常（有鉴权的再加 1 权限）
- 每条业务规则至少：1 正向 + 1 边界
- 每个状态转换：正常路径 + 至少 1 条非法转换
- P0 用例数 > 0（核心功能必须有 P0）

展示矩阵后等用户确认，再进入 Phase 4。
</HARD-GATE>

确认话术：

```
共 N 条用例（P0: X / P1: Y / P2: Z），覆盖 <接口数> 个接口、<规则数> 条业务规则。
1. ✅ 确认
2. ❓ 需要补充：<说明>
```

## Phase 4 — 输出

1. 用例落盘到 `docs/test-cases/<feature>.md`（或 `.claude/local/<feature>/test-cases.md` 做临时探索）
2. 生成**测试骨架**（只有方法名 + TODO 注释，不含实现），语言按本仓库技术栈：

```
test("should create order when input is valid", () => { /* TODO */ });
test("should reject when productId is null", () => { /* TODO */ });
```

3. 输出覆盖统计：

```yaml
coverage:
  targets: <接口/函数总数>
  covered: <被用例覆盖数>
  ratio: <百分比>
distribution: { unit: n, integration: n, e2e: n, p0: n, p1: n, p2: n }
```

## 与其他 skill 的分工

| 场景 | 用哪个 |
|---|---|
| 从需求 / 方案生成用例矩阵 | **本 skill** |
| 评估一次改动的影响 + 已有覆盖 + 回归风险 | `change-review-package` |
| 评审技术方案文档本身 | `tech-doc-review` |

串联方式：`change-review-package` 的 Phase 3 发现"❌ 未覆盖" → 用本 skill 为这些影响点生成用例。

## Anti-Patterns

| 反模式 | 正确做法 |
|---|---|
| 只写正常路径 | 异常与边界才是 bug 高发区 |
| 用例预期写"返回正确结果" | 预期必须可断言：具体状态码 / 字段 / 错误码 |
| 一条用例验证多个点 | 拆开，失败时才能定位 |
| 生成完就当测试写完了 | 本 skill 只产清单，实现要另做 |
