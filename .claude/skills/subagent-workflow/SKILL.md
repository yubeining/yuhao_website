# Subagent 协作工作流

## Overview

Subagent 的两个价值：**并行多视角审查**，以及**把大量探索性读取隔离在主线索之外**（主上下文保持干净）。
但 subagent 的输出必须经主 agent 审核才能作为行动依据——**subagent 是顾问，主 agent 是决策者，用户是审批人**。

## When to Use

- 要读 ≥5 个文件 / 探索量大 / 跨目录全局搜索 → 隔离到 subagent，主线索只收摘要
- 同一段代码需要多视角并行审查（正确性 / 安全 / 性能）
- 独立的审查类工作（方案审查、代码审查）

## When NOT to Use

- 读 1-2 个已知路径的文件（启动开销反而亏）
- 单目录简单搜索
- 需要完整对话历史的连续任务（subagent 没有主线索上下文）
- 紧急修复（直接干，不做多角度审查）

## 角色定义（内联，无需额外文件）

| 角色 | 职责 | agent 类型 |
|---|---|---|
| **explorer** | 定位代码 / 找调用点 / 摸清某模块结构，只回报结论 | 只读探索类 |
| **spec-reviewer** | 审查需求 / 技术方案文档的完整性、一致性、风险 | 只读 |
| **code-reviewer** | 从正确性、安全、性能、风格四个维度审查一段改动 | 只读 |
| **test-auditor** | 核查改动是否有对应测试、断言是否真的覆盖到改动分支 | 只读 |

派发时把角色名写进 prompt 第一行，约束它别越界。

## 编排模式

**模式 1 — 并行审查**：主 agent 同时派发 spec-reviewer / code-reviewer / test-auditor，
各自独立产出报告 → 主 agent 汇总去重 → 输出统一结论。适合交付前全面检查。

**模式 2 — 顺序流水线**：spec-reviewer（方案）→ 通过 → 编码 → code-reviewer（实现）→ test-auditor（覆盖）。
适合完整开发流程，每段依赖上一段输出。

**模式 3 — 专家委派**：按当前任务类型派给最合适的单个角色。适合日常开发。

## 交互协议

派发给 subagent 的 prompt 必须**自包含**：

```markdown
## 角色
<explorer / spec-reviewer / code-reviewer / test-auditor>

## 任务上下文
- 仓库技术栈：<…>
- 相关文件：<精确路径列表>
- 具体要求：<审查重点，越具体越好>
- 不要做什么：<明确越界边界，如"不要修改文件"、"不要评论风格偏好">

## 参考规范
- .claude/rules/core.md
- <相关 SKILL.md 路径>

## 返回格式
见下方"报告格式"，正文 ≤200 字 + 问题清单。
```

返回报告格式：

```markdown
## <角色> 审查报告

### 审查范围
<读了什么、没读什么>

### 发现的问题
#### CRITICAL（必须修复）
- [ ] <问题 + 建议修复方案>
#### HIGH（强烈建议）
#### MEDIUM（建议改进）
#### LOW（可选）

### 结论
通过 / 有条件通过 / 不通过

### 置信度
高 / 中 / 低 — <对自身判断的置信度说明>
```

## 两阶段审查

<HARD-GATE>
**阶段 1 — subagent 独立审查**：按角色定义独立完成，输出结构化分级报告；subagent 之间**不直接交互**。

**阶段 2 — 主 agent 综合审查**：收集全部报告 → 检查报告间是否矛盾或遗漏 → 合并重复问题、
统一严重级别 → 形成最终行动建议展示给用户。

禁止不经主 agent 判断就直接执行 subagent 的建议。
</HARD-GATE>

## Red Flags

| 信号 | 动作 |
|---|---|
| 多个 subagent 对同一问题结论矛盾 | 主 agent 深入分析矛盾原因，必要时交用户裁决 |
| 报告中 CRITICAL >5 个 | 暂停流程，先解决 CRITICAL |
| subagent 自报置信度"低" | 不采纳，转人工确认 |
| subagent 审查范围越界 | 忽略越界意见，重新派发 |
| subagent 返回的是原始数据堆 | 要求重新以结论摘要形式返回，否则主线索被污染 |

## Anti-Patterns

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 所有任务都派 subagent | 简单任务被过度复杂化 + 启动开销 | 只在并行 / 隔离 / 专业化有明确收益时用 |
| 直接执行 subagent 建议 | 执行了错误或矛盾的建议 | 主 agent 必须综合审核 |
| subagent 之间互相传话 | 职责不清、消息混乱 | 所有交互经主 agent 中转 |
| 忽略"低置信度"标记 | 基于不确定判断做决策 | 低置信度必须人工确认 |
| 一个 subagent 兼多角色 | 审查质量下降 | 一个 subagent 专注一个角色 |
| prompt 假设 subagent 知道上文 | subagent 瞎猜 | prompt 必须自包含 |
