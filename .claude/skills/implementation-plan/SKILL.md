# 实施计划

## Overview

把"方案"拆解成细粒度步骤，每步 2-5 分钟，包含精确文件路径、预期代码变更和验证命令。
**没有实施计划的编码 = 走一步看一步 = 返工。**

## When to Use

- 方案已确认，准备开始编码
- 需要把大任务拆成可执行小步
- 命中了 `.claude/rules/core.md` 的 Plan-First 阈值

## When NOT to Use

- 单行配置修改或拼写错误
- 紧急修复（直接进 systematic-debugging）
- 方案本身还没定（先定方案）

<HARD-GATE>
实施计划必须在编码开始前完成并获得确认。必须：
1. 拆成每步 2-5 分钟的具体步骤
2. 每步包含：精确文件路径、预期变更、验证命令
3. 用户确认后才能开始 Step 1

在此之前禁止生成任何生产代码。跳过计划直接编码 = 方向错了就浪费全部时间。
</HARD-GATE>

## 计划模板

```markdown
# 实施计划 — <功能名称>

## 基本信息
- 方案 / 需求出处：<链接或路径>
- 预估：N 步，约 X 分钟
- 前置条件：<已完成的事项 / 依赖>

## 步骤列表

### Step 1: <简短描述>（约 X 分钟）
- **文件**：`path/to/file.ext`（新建 / 修改）
- **操作**：<具体做什么>
- **预期变更**：
    <关键代码片段或签名，不必写全量实现>
- **验证**：<可直接执行的命令>
- **检查点**：<怎么判断这步成功了>

### Step 2: ...
```

## 拆解粒度

| 粒度 | 耗时 | 判断 | 例子 |
|---|---|---|---|
| 过细 | <2 分钟 | 不该单独成步 | "加一个 import" |
| **合适** | 2-5 分钟 | 目标粒度 | "创建 OrderService 骨架 + 方法签名" |
| 过粗 | >10 分钟 | 必须再拆 | "实现订单模块" |

拆解原则：

1. **每步一个关注点** — 不在一步里同时建 model 和 service
2. **每步可验证** — 每步结束都有一条命令能验证
3. **步骤间低耦合** — 尽量每步独立可回滚
4. **先测试后实现** — 测试步骤排在实现步骤之前

## 典型顺序（按本仓库实际分层替换）

```
Step 1: 数据结构 / 类型定义（schema / model / type）
Step 2: 数据访问层骨架
Step 3: 业务逻辑单元测试（RED）
Step 4: 业务逻辑实现（GREEN）
Step 5: 入口层（API / CLI / handler）
Step 6: 入口层测试
Step 7: 端到端手动验证
```

每步验证用 `.claude/rules/core.md` 的命令表，**按分档选**：默认迭代档（单测试文件），
命中"≥20 文件 / 跨层 / 风险点"才升模块档。

## 验证检查点

| 检查项 | 方式 |
|---|---|
| 编译通过 | build 命令无错误 |
| 测试通过 | 新增测试 + 相关已有测试均 PASS |
| 无副作用 | 未改动的功能仍正常 |
| 符合规范 | lint 无新增警告 |

每步完成后输出：`✅ Step X 完成 — <验证结果摘要>` → 继续下一步。

<HARD-GATE>
某步验证未通过：
1. 禁止跳过该步继续下一步
2. 必须先修复当前步骤
3. 3 次修复失败 → 转 systematic-debugging

在错误基础上继续构建 = 最终全部返工。
</HARD-GATE>

## Red Flags — 计划需要调整

| 信号 | 应对 |
|---|---|
| 单步超过 10 分钟没完成 | 粒度过粗，当场再拆 |
| 步骤顺序反复调整 | 依赖关系没理清，回头梳理依赖链 |
| 多个步骤都卡在同一个未完成步骤上 | 关键路径瓶颈，优先打通它 |
| 实际代码与计划预期差异 >50% | 方案可能有遗漏，暂停编码回到方案 |

## Anti-Patterns

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| "我先写着看" | 方向错了浪费全部时间 | 先计划，确认后编码 |
| 步骤只写描述不写文件路径 | AI 猜文件位置 | 每步必须精确路径 |
| 跳过验证 | 错误累积，最后集中爆发 | 每步必验 |
| 一步做太多事 | 出错无法定位 | 拆到 2-5 分钟 |
| 计划里没有测试步骤 | 测试沦为事后补充 | 测试步骤在实现之前 |
