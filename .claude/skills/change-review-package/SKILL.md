# 改动评审包

为当前分支相对基准分支的所有变更，生成一份**交付给 reviewer / 自己复核用**的完整包：
**影响面 + 测试覆盖 + 回归风险 + 手动测试用例 + 行动项**。

## 核心原则

**分析，不生成。** 本 skill 不写代码、不写单测，只产出"给评审看的交付物"。
发现需要补单测 → 只标注，实际写测试去用 `test-case-design`。

## When to Use

- 交付 / 合并前，需要说清改动的影响范围
- 改动跨多个模块，需要识别隐性影响
- 修改了既有功能（非纯新增），需要评估回归风险
- 需要回答"哪些测了？哪些没测？哪些必须手动测？"

**不适用**：纯新增零依赖的孤立模块（直接用 `test-case-design`）；仅改文档 / 注释；代码还没稳定。

<HARD-GATE>
单元测试已覆盖的场景**禁止**再写入手动测试清单（Phase 5）。
每条手动用例必须填写"不可被单测替代的原因"，填不出来就从清单中删除。

违反此约束 = 把重复劳动甩给执行人 + 误导 reviewer 对真实测试缺口的判断。
</HARD-GATE>

## Phase 1 — 变更收集

```bash
BASE=${BASE:-main}                       # 本仓库主干分支名不是 main 就改这里
HEAD=$(git rev-parse --abbrev-ref HEAD)

git diff --name-status "$BASE"...HEAD    # 文件清单（A/M/D/R）
git diff --stat "$BASE"...HEAD           # 行数统计
git diff "$BASE"...HEAD -- <file>        # 逐文件详细 diff
```

必须记录：

- 文件路径 + 变更类型（新增 / 修改 / 删除 / 重命名）
- 每个文件的**核心改动语义**（新增函数？改逻辑？改签名？）
- 被删除 / 重命名的旧符号 → 进入"调用方排查"清单

## Phase 2 — 影响点识别

对每个变更文件按角色定位影响：

| 文件角色 | 影响点定位规则 |
|---|---|
| 对外入口（HTTP handler / CLI / RPC） | 路径、请求响应契约、鉴权 → 影响所有调用端 |
| 业务逻辑层 | 公开函数签名、内部分支、事务边界 → 影响所有调用方 |
| 数据访问层 / SQL | 查询语义、新增字段、索引使用 → 影响性能 + 数据一致性 |
| 数据模型 / 类型定义 | 字段增删改类型 → 影响序列化、迁移、所有引用方 |
| 配置 / 环境变量 | 环境差异、默认值 → 必须人工验证 |
| 公共工具 / 通用函数 | 影响范围最广，必须排查**所有**调用点 |
| 前端组件 / 共享 hook | 影响所有依赖它的页面 |
| 迁移脚本 / DDL | 影响上线流程、数据兼容性、回滚 |

排查命令（按本仓库语言调整 include 范围）：

```bash
grep -rn "functionName(" --include='*.<ext>' .   # 找调用点
grep -rn "TypeOrClassName" --include='*.<ext>' . # 找引用点
```

**输出**：每个变更文件列出"直接影响 + 间接影响"两层。禁止只写"无影响"——
要么给出 grep 证据说明没有调用方，要么列出影响点。

## Phase 3 — 现有测试覆盖核查

只核查，不写新测试。

1. 定位测试文件（按本仓库约定：同目录 `*.test.*` / `*.spec.*` / `tests/` / `src/test/`）
2. **读测试方法名和断言**，不是看文件存在就算覆盖
3. 与 Phase 2 影响点逐项映射：

```markdown
| 影响点 | 测试文件 | 已覆盖的测试 | 状态 |
|---|---|---|---|
| serviceA.method1 新增分支 | serviceA.test.ts | returns X when caseA | ✅ 已覆盖 |
| serviceA.method2 改逻辑 | serviceA.test.ts | （无相关测试） | ❌ 未覆盖 |
| serviceB.method3 签名变更 | serviceB.test.ts | 旧断言 | ⚠️ 需更新 |
```

状态标记：

- ✅ 已覆盖 — 测试名/断言能明确对应到本次改动的分支
- ❌ 未覆盖 — 影响点无对应测试 → 建议新增
- ⚠️ 需更新 — 测试存在但行为已变，断言已失效
- 🔧 不适合单测 — 依赖外部系统 / UI 渲染 → 转入 Phase 5 手动测试

## Phase 4 — 回归风险评估

**回归风险 = 改动让"原本通过的功能"开始失败的风险。** 8 个维度逐一过，每个维度必须明确写"无风险"或具体风险：

| 维度 | 高风险信号 | 排查动作 |
|---|---|---|
| 签名变更 | 改了公开函数参数 / 返回值 | 列出所有调用点，确认已同步 |
| 分支增删 | if / else / switch 增减 | 已有测试是否仍覆盖原分支 |
| 共享状态 | 改了全局变量 / 缓存 / 单例 | 并发场景 + 初始化顺序 |
| 数据库 | 改 SQL / 索引 / 字段 | 旧数据兼容性 + 慢查询 |
| 对外契约 | API 字段变更 / 删除 | 调用端是否同步 |
| 事务 / 原子性 | 事务边界、传播行为变更 | 是否仍能正确回滚 |
| 异步 / 事件 | 发布订阅变更 | 重试、幂等、顺序 |
| 依赖升级 | 第三方库版本变更 | 破坏性变更 + 锁文件 |

```markdown
| 风险项 | 等级 | 触发条件 | 缓解措施 |
|---|---|---|---|
| serviceA.method1 签名变更影响 handlerX | 高 | 调用方未同步 | 已检查全部调用点 + 编译通过 |
| 新增查询缺索引 | 中 | 数据量 >10w 变慢 | EXPLAIN 验证 + 上线观察 |
```

等级：**高** = 可能导致事故 / 数据错误 / 功能不可用；**中** = 性能退化 / 边界出错；**低** = 仅限新功能内部。

## Phase 5 — 手动测试场景（去重）

**铁律：单测已覆盖的场景禁止列入。** 仅以下情况才补手动测试：

| 必须手动测 | 原因 |
|---|---|
| 跨模块端到端流程 | 单测只覆盖单点 |
| 真实外部 API 调用（支付 / 推送 / 第三方） | 单测用 mock |
| 真实 DB 执行 + 索引命中 | 单测用内存库 / mock |
| UI 交互、视觉、跨浏览器 / 设备 | 单测覆盖不到 |
| 权限 / 会话 / 多租户隔离 | 依赖完整运行时上下文 |
| 并发竞争、幂等、锁冲突 | 单测难以稳定复现 |
| 定时任务、消息消费 | 依赖运行时调度 |
| 环境 / 配置差异 | 单测用统一配置 |
| Phase 4 标记为"高"的既有功能回归 | 必须人工确认 |

用例格式：

```markdown
### TC-001: <体现业务场景的标题>
- **关联影响点**：<Phase 2 中的影响点>
- **类型**：E2E / 集成 / 回归 / 性能 / 权限
- **优先级**：P0 / P1 / P2
- **前置条件**：<环境、数据>
- **操作步骤**：1. … 2. …
- **预期结果**：<可断言的具体结果>
- **不可被单测替代的原因**：<一句话>   ← 强制字段，填不出就删掉这条
```

起草完成后，逐条与 Phase 3 的"已覆盖"对照，重复的删除。

## Phase 5.5（可选）— 接口请求集合

**仅当本 PR 改动了 HTTP 接口时才做**；没有 HTTP 接口则在报告里明示"本次未触及 HTTP 接口，跳过"。

- 只导出**本次新增 / 修改**的接口（来源 = Phase 1 的 diff），不导出未变更接口
- **每条 Phase 5 的 TC 至少对应 1 个独立请求**；同一接口的不同参数变体（正常 / 异常 / 边界 / 旧路径）
  禁止合并成一条——合并等于把测试设计责任甩回给执行人
- 异常路径（4xx / 业务错误）必须独立成条，并写明期望的错误码与 message 片段
- 参数填**能跑的示例值**（ID 占位 `1`、枚举填第一个合法值并在注释里列全部合法值），
  让执行人"改改就能跑"
- 不写断言脚本（留给执行人自填），但每条必须写 `Linked TC: TC-xxx` 做双向关联
- 落盘形式按本仓库现状选（Postman Collection v2.1 JSON / `.http` 文件 / curl 脚本），
  路径与报告同目录；JSON 产物落盘前必须能被 `python3 -c "import json;json.load(open('<f>'))"` 解析

## Phase 6 — 报告输出

保存到 `docs/impact-reports/YYYY-MM-DD-<branch>-impact.md`（目录不存在就建）。

```markdown
# 改动评审包 — <branch>

> 生成时间：YYYY-MM-DD HH:mm ｜ 基准：<base> ｜ 变更文件：N（新增 a / 修改 b / 删除 c）｜ +X / -Y 行

## 1. 变更摘要
| 文件 | 角色 | 类型 | 核心改动 |

## 2. 影响点清单
### 2.1 <file>（修改）
- 直接影响：…
- 间接影响：…

## 3. 测试覆盖核查
（Phase 3 表格）
**未覆盖统计**：N 个影响点未覆盖。

## 4. 回归风险评估
（Phase 4 表格，8 个维度都要出现）

## 5. 手动测试用例（去重后）
（Phase 5 格式）

## 6. 行动项
- [ ] 补单测：…
- [ ] 更新单测：…
- [ ] 手动验证：TC-001、TC-002
- [ ] （如有）导入接口请求集合：<文件>

## 7. 结论
- 单测覆盖：X / Y 个影响点（Z%）
- 高风险项：N 个 → 已 / 未缓解
- 是否可合并：✅ / ⚠️ 需先完成行动项
```

## 常见误区

| 误区 | 正确做法 |
|---|---|
| 把单测能覆盖的场景写进手动测试 | Phase 5 强制填"不可被单测替代的原因" |
| 只看 diff 不看调用方 | Phase 2 必须 grep 调用点 |
| 跳过回归风险评估 | Phase 4 是报告核心，禁止省略 |
| 标"已覆盖"只看测试文件存在 | 必须读测试名 + 断言 |
| 把"建议补的单测"写进报告就算完成 | 报告只标注；写测试用 `test-case-design` |
| 报告写了不交付 | Phase 6 必须落盘并在交付说明里引用 |

## 完成标准

- [ ] 所有变更文件都在 Phase 1 清单里
- [ ] 每个变更文件都有影响点（不能只写"无影响"）
- [ ] 每个影响点都有覆盖标记
- [ ] Phase 4 的 8 个维度都明确标注了"无风险"或具体风险
- [ ] 每条手动用例都有"不可被单测替代的原因"
- [ ] 报告 7 节齐全，行动项可勾选
