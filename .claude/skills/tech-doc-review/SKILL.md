# 技术文档评审

评审**文档**，不是评审代码。核心价值在于捕捉「文档说的」与「代码做的」之间的鸿沟，
以及「没写的」比「写错的」更危险的那部分。

## When to Use

| 场景 | 侧重 |
|---|---|
| 技术方案完稿，进入评审 | 四层全跑 |
| 接收外部 / 跨团队技术方案 | 四层全跑 + 代码交叉验证 |
| 只评 API 设计 / DB schema | Phase 0 分类后按单一 lens 深入 |
| 已落地方案复盘 | 以 Phase 3 扩展性深挖为主 |

**不要用本 skill**：评审代码（用 code review）；撰写新方案（本 skill 只评不写）。

## Severity 分级

| 等级 | 含义 | 是否阻断 |
|---|---|---|
| 🔴 **Must Fix** | 技术方向错误、安全漏洞、数据丢失风险、已知会导致事故 | **是** |
| 🟡 **Should Fix** | 缺异常处理、扩展性隐患、文档与代码不一致、关键信息缺失 | 否（强烈建议） |
| 🟢 **Nice to Have** | 格式、示例、措辞、非关键路径 | 否 |
| 💬 **Discussion** | 多个合理选择 / 需更多上下文 / 我的理解可能有偏差 | 否 |

### Severity 决策树

```
不修复会导致：
├── 事故 / 数据丢失 / 安全漏洞？          → 🔴 Must Fix
├── 明显的性能 / 扩展性 / 可维护性问题？
│   ├── 6 个月内会暴露？                 → 🟡 Should Fix
│   └── 更远期？                        → 🟢（写进扩展性分析）
├── 文档与代码不一致？
│   ├── 影响读者理解系统行为？            → 🟡 Should Fix
│   └── 只是表述差异？                   → 🟢
├── 信息缺失？
│   ├── 会导致实施者做错决策？            → 🟡 Should Fix
│   └── 只是不够完美？                   → 🟢
└── 我只是不同意（但逻辑自洽、风险可控）？ → 💬 Discussion（不阻塞）
```

## Phase 0 — 分类 + 上下文

### 0.1 文档类型 → 权重

| 类型 | 主评审视角 | 权重（方向 / 决策 / 完整性 / 可执行） |
|---|---|---|
| 架构设计 | 方向 + 决策质量 + 扩展性 | 30 / 30 / 25 / 15 |
| API 设计 | 契约准确性 + 向后兼容 + 安全 | 15 / 25 / 35 / 25 |
| 数据库设计 | 数据建模 + 扩展性 + 性能 | 15 / 30 / 30 / 25 |
| RFC / 决策记录 | 问题定义 + 方案论证 + trade-off | 35 / 35 / 20 / 10 |
| 运维手册 / SOP | 可执行性 + 异常覆盖 + 回滚 | 10 / 15 / 35 / 40 |

别用"架构评审"的标准去苛求一份运维手册。

### 0.2 上下文澄清（缺失就问）

```
1. 目标读者是谁？（团队内 / 跨团队 / 外部）
2. 当前阶段？（草稿征求意见 / 正式评审 / 已进开发需修订）
3. 有没有对应代码可以交叉对照？
4. 有没有特别关注的维度？（安全 / 性能 / 成本 / 兼容性）
```

草稿阶段偏探索性、战略性；上线前偏严格、具体。

### 0.3 关联代码扫描（有代码访问时）

这是"P9 评审"与"表面阅读"的分水岭：

- 找文档涉及的核心模块，扫描其真实结构
- 对比文档里的接口签名 vs 代码实际定义
- 查现有数据模型，确认 schema 兼容性与命名冲突
- 查配置 / 环境变量，确认部署假设成立
- 扫 `TODO` / `FIXME` / `HACK`，暴露文档未提的技术债

重点找：文档说的和代码做的不一致；文档假设了不存在的能力；代码有隐含约束但文档没提。

## Phase 1 — 四层评审（从高杠杆到低杠杆）

**不要从查错别字开始。**

### Layer 1：方向性判断

- 核心问题是什么？定义准确吗？scope 太大还是太小？
- 是不是用复杂方案解决一个本不该存在的问题？
- 与系统整体演进方向一致吗？是加法还是技术债？
- 有没有更简单的方式（YAGNI）？
- 如果方案成功，半年后系统变成什么样？那个状态是想要的吗？

红旗：问题描述模糊直接跳方案；方案复杂度远超问题本身；与现有惯例不一致但未说明原因；
隐含架构大改却表述为"小优化"。

### Layer 2：决策质量

- 每个关键决策是否列出备选方案？放弃的理由经得起推敲吗？
- trade-off 是否诚实呈现？有没有只讲优点不讲代价？
- 约束是真实约束还是人为假设？
- 关键假设不成立时（数据量 10x、并发 5x），决策还成立吗？
- 可逆性如何？回退成本多大？

红旗：只有一个方案（方案 = 结论 without 推理）；对比维度不一致；引用"业界最佳实践"但不说上下文；
选型只看功能匹配不看运维成本和学习曲线；**所有 trade-off 都偏向同一方案**（通常意味着分析不客观）。

### Layer 3：完整性与盲区

**没写的比写了的更危险。** 逐维度核查：

- **错误处理** — 失败场景覆盖？部分失败怎么办？幂等性？
- **数据一致性** — 并发一致性？数据迁移？跨服务事务？
- **安全** — 认证授权？输入校验？敏感数据脱敏？新增攻击面多大？密钥怎么管？
- **性能** — 慢查询 / 全表扫描？N+1？大事务？缓存策略（穿透 / 击穿 / 雪崩 / 与 DB 一致性）？
- **可观测性** — 日志级别与结构化？链路 ID 贯穿？关键指标（成功率 / 错误率 / 耗时）？告警阈值？
- **运维** — 部署方案？回滚？开关 / 灰度？凌晨三点被叫起来能定位吗？
- **向后兼容** — 破坏性变更？老调用方？客户端版本兼容？

### Layer 4：可执行性与可读性

- 目标读者能否**仅凭这份文档**实施？
- 术语命名与代码、其他文档一致吗？
- 示例（请求 / 响应 / SQL / 配置）充足吗？
- 前置条件和依赖明确吗？时间线现实吗？
- 长段落能否拆分？复杂流程有没有图？缩略词首次出现时解释了吗？

## Phase 2 — 代码交叉验证（有代码时）

针对性验证，不是完整 code review：

- **接口一致性** — 文档签名 vs 代码定义（参数名、返回值、字段）
- **数据模型兼容性** — 新表 / 字段 vs 现有 schema（命名冲突、索引、外键）
- **模式一致性** — 新设计 vs 既有惯例（错误处理、分层、命名）
- **依赖真实性** — 文档假设的服务 / 库 / 基建是否真实可用
- **技术债暴露** — 新方案是否建在已知问题之上

无代码访问 → 跳过本阶段，在报告里标注「未做代码验证」，并把"文档与代码不一致"类问题降级为 💬。

## Phase 3 — 扩展性深挖

看 6-12 个月后这套设计如何 age：

| 维度 | 要问的问题 |
|---|---|
| 规模韧性 | 业务量 10x 时哪个组件先撑不住？数据量怎么办？有状态组件的瓶颈？ |
| 变更韧性 | 需求变更时改动范围多大？核心抽象稳定吗？策略变更要改代码还是改配置？ |
| 集成友好度 | 别的系统能否轻松集成？集成点清晰吗（API / 事件 / hook）？引入了不必要的耦合吗？ |
| 运维成熟度 | 上线第一个月 / 第一个季度会遇到什么？迁移过渡期怎么管？容量何时需扩？ |
| 死亡场景 | 最可能在什么情况下失败？单点在哪？级联故障路径？最坏爆炸半径多大？ |

## Phase 4 — 报告

```markdown
# 技术文档 Review：<文档标题>

**类型**：<architecture / api / db / rfc / runbook>　**日期**：YYYY-MM-DD　**阶段**：<草稿 / 正式评审 / 已进开发>

## 总体评价
<2-3 句：方向是否正确、方案质量如何、主要风险在哪>

**结论**：✅ 可以推进 / ⚠️ 需修改后推进 / 🔴 需重大修改

## 关键发现

### 🔴 阻塞性问题（Must Fix）
1. **<标题>**
   - 位置：<章节 / 代码位置>
   - 问题：<具体描述>
   - 影响：<不修复的后果>
   - 建议：<具体改进方向>

### 🟡 重要建议（Should Fix）
### 🟢 优化建议（Nice to Have）
### 💬 讨论点（Open Questions）

## 扩展性分析
<Phase 3 结果，聚焦最关键 1-2 个维度>

## 代码交叉验证
<Phase 2 发现；无代码访问则写「未做代码验证」>

## 遗漏清单
<Layer 3 发现的缺失，按重要性排序>
```

## 评审原则（怎么 review，而非 review 什么）

| 原则 | 说明 |
|---|---|
| **提问优于断言** | ✅「这里选 Redis 不用本地缓存的原因？QPS 预期多少？」❌「应该用本地缓存。」 |
| **区分"不同意"和"有问题"** | 方案不是你会选的、但逻辑自洽风险可控 → **放行**。把住底线和方向，不是每个实现细节 |
| **缺了什么 > 写错什么** | 最常见问题不是写错，而是遗漏。「想过但决定不需要」≠「根本没想到」 |
| **代码是事实** | 文档与代码冲突时，先验证代码行为，再决定改文档还是改代码 |
| **用时间轴思考** | 不只评估"现在能不能工作"，而是"6-12 个月后是否还能工作" |
| **爆炸半径意识** | 出问题影响一个接口、一个服务、还是整个系统？ |

## 评审者反模式

| 反模式 | 例子 | 修正 |
|---|---|---|
| 刷漆棚 | 花 30 分钟讨论一个内部变量命名 | 优先 Layer 1-2，小问题标 🟢 |
| 改成自己的写法 | 重写整段描述只是换表述 | 只在影响理解时才建议修改 |
| 因格式阻塞 | 没画图就不批准 | 格式问题永远 🟢，不是 🔴 |
| 只提问题不给方向 | 「这里有问题」 | 每个 🔴 / 🟡 必须附具体建议 |
| 用身份压人 | 「听我的」 | 用具体场景、数据、推理链支撑 |
| 越界加需求 | 评 API 时要求加全新模块 | 记为 future consideration，不阻塞当前 |

<HARD-GATE>
报告中存在 🔴 Must Fix 时，禁止输出「Approved」结论。必须：
1. 列全 🔴 项，每项含位置 / 影响 / 建议
2. 通知作者修订后重审
3. 修订后仍存在 🔴 → 升级给更高层决策

未解决 🔴 就放行 = 评审形同虚设。
</HARD-GATE>

## Appendix — 分类型 checklist

**架构设计**：问题陈述 / 上下文与约束（哪些可商量）/ 方案概览（一段话或一张图说清）/
≥2 个备选且评估维度一致 / 详细设计（接口、数据流、状态流）/ 风险与应对（概率 × 影响）/
上线方案（灰度、回滚、迁移、兼容）/ 可量化成功指标（不接受"提升用户体验"）。

**API 设计**：命名一致性（camelCase vs snake_case）/ HTTP 语义准确 / 状态码（400 vs 422、201、204）/
统一错误格式（code + message + details）/ 分页（offset vs cursor）/ 版本策略 /
破坏性变更评估（删字段、改类型、加枚举值）/ 认证授权 + 输入校验 + 脱敏 + 限流 /
写操作幂等（幂等键）/ 每接口 ≥1 正常 + 1 异常示例。

**数据库设计**：命名规范（布尔 `is_`/`has_`、时间 `_at`）/ 索引（高频 WHERE 有索引、联合索引最左前缀、无冗余）/
类型（金额用定点数不用浮点、状态用小整数 + 枚举、整型宽度）/ 范式（OLTP ≥3NF、反范式要有同步机制）/
规模（单表预期多大、分表、大字段拆分、归档）/ 迁移安全（大表 ALTER 锁表、加非空列要有默认值、分步、回滚）。

**运维手册**：冷启动测试（不了解背景的人能否只凭文档完成）/ 每步失败如何判断和处理 /
部分完成如何恢复 / 每步有回滚且验证过 / 升级路径（什么情况找谁、联系方式是否最新）。
