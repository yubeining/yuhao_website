# 系统化调试

## Overview

系统化调试是防止"乱枪打鸟"式修复的关键。AI 最危险的调试模式是"看到错误就猜测修复"——
这会掩盖根本原因、引入新问题，并且让后续每一次修复都建立在错误的理解上。

## When to Use

- 遇到任何 bug 或异常行为
- 测试失败且原因不明显
- 线上告警
- 性能退化

## When NOT to Use

- 错误信息明确指向拼写错误（直接修）
- 编译错误有明确行号和原因（直接修）

<HARD-GATE>
禁止未完成根因调查就提出修复方案。必须：
1. 完成阶段 1（根因调查）和阶段 2（模式分析）
2. 形成至少一个**可验证**的假设
3. 用最小改动验证该假设

在此之前，任何"我觉得问题是…"的猜测都不允许转化为代码修改。
</HARD-GATE>

## 四阶段流程

### 阶段 1：根因调查

1. **完整阅读错误信息** — 不要只看第一行；读完整 stack trace / 日志上下文
2. **稳定复现** — 找到可靠的复现步骤；无法复现就先解决"无法复现"
3. **检查最近变更** — `git log --oneline -10`、`git diff HEAD~3`、`git log -p -- <可疑文件>`
4. **追踪数据流** — 从入口到出错点画出完整链路，标出每一跳的输入输出

### 阶段 2：模式分析

1. 在代码库中寻找**类似且正常工作**的代码
2. 逐项比较差异：正常 vs 异常，差在哪一个变量/调用/配置
3. 检查是否是已知模式：搜项目 issue、注释里的 TODO/FIXME、历史提交信息

### 阶段 3：假设验证

1. 形成**单一**假设（不要同时测试多个）
2. 做最小可能的改动来验证
3. 一次只改一个变量
4. 记录每次尝试的结果（改了什么 → 现象如何变化）

### 阶段 4：实施修复

1. 先写**能复现该 bug 的回归测试**（RED）
2. 实施修复
3. 确认测试通过（GREEN）
4. 跑改动模块的测试，确认没引入新问题

## 通用症状 → 排查入口

| 症状 | 第一步看哪里 |
|---|---|
| 偶发、重试就好了 | 并发 / 竞态 / 缓存 / 超时重试；先找共享可变状态 |
| 只在某个环境出现 | 配置与环境变量 diff，不要先怀疑代码 |
| 数据对不上但无报错 | 沿数据流打点，定位第一次出现错误值的位置（二分法） |
| 改 A 坏 B | 找隐式共享：全局状态、单例、缓存、模块级变量 |
| 性能突然变差 | 先测量再优化：找出放大倍数（循环内 IO / N+1 / 无索引查询） |
| 测试本地过 CI 挂 | 时间、时区、随机、文件顺序、并行度、残留脏数据 |
| 报错指向第三方库 | 先验证自己的入参；库的 bug 是最后一个假设，不是第一个 |

## 3 次失败规则

<HARD-GATE>
同一问题已尝试 3 次修复仍未解决：
1. 立即停止尝试
2. 总结已尝试的方法和各自结果
3. 提出需要人类决策的具体问题（含你认为最可能的两个方向）
4. 等待人类决定

继续盲目尝试只会浪费时间并引入更多问题。
</HARD-GATE>

## Red Flags — 升级信号

| 警告信号 | 升级动作 |
|---|---|
| 只在生产复现，本地无法复现 | 先拿到生产日志 / 环境快照，不要在本地猜 |
| 涉及多个服务的分布式问题 | 拉齐相关服务负责人，先对齐时序再查代码 |
| 数据损坏或数据不一致 | 立即停止写操作，先评估影响面和是否需要数据修复 |
| 安全相关 | 立即上报，不要在公开渠道贴复现步骤 |
| 3 次修复尝试均失败 | 停止独自调试，发起技术讨论 |

升级不是失败，沉默才是。
