# Core Engineering Rules

> 本文件是本仓库 AI 协作的核心约束，始终生效。编码、调试、Review 全程遵守。
> 与本仓库「可执行检查」（hook / lint / CI 脚本）冲突时，**一律以可执行检查为准**（见末节优先级表）。

## [CRITICAL] 五条核心原则

1. **先设计后编码** — 复杂功能先产出方案，获批后再进入编码
2. **测试驱动** — 先写测试再写实现
3. **安全优先** — 禁止硬编码任何密钥；所有外部输入必须校验
4. **不可变性** — 优先创建新对象，避免原地修改已有数据
5. **证据先于结论** — 必须执行验证命令并确认输出，才能声称"完成"

## [HIGH] Think Before Coding — 显式化假设与歧义

- 编码前必须说出假设（"我假设 X 是…"），禁止默默选择
- 需求有多种解读时，**全部**摆出让用户选，禁止挑一个就做
- 存在更简单解法时必须主动反驳，不能因"用户已指定方案"就放弃质疑
- 不清楚 → 停下来问，禁止"猜着做"

## [CRITICAL] 禁止用语清单

声称任务完成时，以下用语绝对禁止：

| 禁止用语 | 必须替代为 |
|---|---|
| "应该没问题" | 实际执行结果 + exit code |
| "看起来正确" | diff 对比 / 测试通过的输出 |
| "大概能用" | 完整测试执行日志 |
| "我觉得可以" | 验证命令的完整输出 |

## [CRITICAL] 完成验证 — HARD-GATE

<HARD-GATE>
声称任何任务完成之前，依次执行，缺一不可：

1. **确定验证命令** — 见下方命令表
2. **执行完整命令** — 必须是本次新执行的，禁止引用之前的运行结果
3. **阅读完整输出** — 确认 exit code 为 0，确认无 ERROR / FAIL
4. **明确报告结果** — 贴出关键输出行，明确声明通过或失败

任何一步未完成，禁止声称完成。
</HARD-GATE>

### 本仓库验证命令

全部在仓库根执行。以下每条都实跑验证过，不是照抄模板。

| 用途 | 命令 |
|---|---|
| 单个测试（迭代档，默认） | `cd backend && mvn test -Dtest=SecurityCspTest` |
| 一个模块的单测（模块档） | `cd backend && mvn test -Dtest='com.mfg.<域>.**'` |
| 一个模块含集成测试 | `cd backend && mvn verify -Dit.test='com.mfg.<域>.**'` |
| 全量测试（回归档，仅提交/合并前） | `cd backend && mvn verify` |
| 后端编译 | `cd backend && mvn -q compile` |
| 前端类型检查 | `cd portal && npm run type-check` |
| 前端构建（含 `tsc -b`） | `cd portal && npm run build` |
| 提交闸门（9 个 diff-aware 检查器） | `.githooks/pre-commit` |

三个必须知道的坑：

- **全量测试是 `mvn verify`，不是 `mvn test`。** `mvn test` **不跑** `*IT.java`
  （CLAUDE.md §9 / §12）。拿 `mvn test` 绿了就说"测试通过"，等于跳过了全部集成测试。
- **跑集成测试前先 `docker compose up -d`**，它们要真 PostgreSQL + 真 Redis，禁止 mock。
- **本仓库没有 lint 工具。** `portal/package.json` 里那条 `lint: eslint src` 是死的 ——
  eslint 不在 dependencies、不在 lockfile，也没有任何配置文件，跑起来 `command not found`、退出码 127。
  自第一个 bootstrap 提交起就是这样，且全仓库**零个调用方**（CI / hook / 构建脚本都不调它），
  所以现在没坏任何东西。静态检查的真源是 `.githooks/pre-commit` 里那 9 个检查器加前端的 `tsc`。
- **测退出码不要接管道。** `npm run lint | tail` 之后的 `$?` 是 `tail` 的退出码，恒为 0 ——
  真实的 127 被吞掉。要么直接跑，要么 `set -o pipefail`。
  这个坑真实发生过：据此得出"lint 静默通过"的错误结论，进而把严重性判高了一档。

## [CRITICAL] Plan-First 复杂度阈值

<HARD-GATE>
满足以下**任一**条件，必须先进入 plan 模式输出方案并等待用户批准，禁止直接动手编码：

| 触发条件 | 例子 |
|---|---|
| 改动涉及 ≥3 个文件 **且** 跨层（入口层 / 业务层 / 数据层 任意 2 层以上） | 新增一个字段要改 route + service + model |
| 涉及接口 / 抽象类 / 枚举 / 公共类型 的新增或语义变更 | 给状态枚举加一个新值 |
| 数据库 schema 变更（DDL / 索引 / 约束） | 新增一张表 |
| 对外协议变更（API 契约 / 事件格式 / 消息字段） | 响应体删字段 |
| 用户输入是模糊指令（"改造一下"/"开启 X"/"按方案执行"），没有具体步骤 | "把通知模块重构一下" |

行为要求：
1. 先输出 (a) 涉及文件清单 (b) 改动顺序 (c) 验证方式 (d) 风险点
2. 收到明确"批准/确认/执行"才能编码；用户提质疑就回到 plan
3. plan 期间只读（Read / Grep / Glob），禁止 Write / Edit
4. plan 获批后禁止扩大范围；新增需求要先回 plan
</HARD-GATE>

例外（可不走 plan）：单文件改动且不涉及接口语义；纯文档 / 注释 / 格式修复；用户明确说"不用 plan，直接改"。

**为什么是 CRITICAL**：无 plan 直接深循环的模糊指令，单条消耗可达数十到上百美元；plan 把"边想边做"的探索成本前置成一次便宜的方案输出。

## [CRITICAL] 分阶段测试策略 — 避免无意义的全量回归

**铁律：测试范围按改动规模分档；禁止小改动触发全量回归。**

| 档位 | 触发条件 | 跑什么 |
|---|---|---|
| **迭代档** | 改动 <20 文件 **且** 未跨层 **且** 风险可控 | 改动文件直接相关的测试（`cd backend && mvn test -Dtest=SecurityCspTest`） |
| **模块档** | 改动 ≥20 文件 **或** 跨层 **或** 命中风险点 | 涉及模块的全部测试（`cd backend && mvn test -Dtest='com.mfg.<域>.**'；该模块有 *IT 时用 cd backend && mvn verify -Dit.test='com.mfg.<域>.**'`） |
| **回归档** | 准备提交 / 合并 / 交付前 | 全量（`cd backend && mvn verify（**不是** mvn test —— 它不跑 *IT.java；跑前先 docker compose up -d）`） |

"风险可控"须**全部**满足，任一不满足即升级为模块档：

- 不涉及接口 / 抽象类 / 枚举 / 公共类型的语义变更
- 不涉及 DDL / 数据库 schema
- 不涉及对外协议（API 契约 / 事件格式 / 消息字段）
- 不涉及安全相关代码（认证 / 授权 / 加密 / 输入校验）

本仓库"一个模块"的单位：后端是一个 Java 包 `com.mfg.platform.<模块>` 或 `com.mfg.domain.<域>`，
前端是一个受众目录 `portal/src/pages/<受众>/`。跨多模块改动 → 把涉及的模块测试全部拼起来跑。

> 本规则关注"测试范围扩张"（<20 / ≥20 文件），Plan-First 关注"要不要先出方案"（≥3 文件且跨层）。
> 两者风险维度不同，**故意不对齐**。

## [CRITICAL] TDD 借口 vs 现实

```
RED:      写失败的测试 → 运行确认失败
GREEN:    写最少代码通过测试 → 运行确认通过
REFACTOR: 重构 → 确认测试仍然通过
```

**铁律：没有失败的测试，就不写生产代码。** 先写了代码再补测试 → 删掉重来。

| 借口 | 现实 |
|---|---|
| "时间不够写测试" | 没有测试的代码返工更久，TDD 节省总时间 |
| "这逻辑太简单不需要测试" | 简单逻辑也会因需求变更引入 bug |
| "我先写代码再补测试" | 补写的测试只验证现有行为，不能驱动设计 |
| "测试太难写了" | 难写说明耦合度高，正是需要重构的信号 |
| "AI 生成的代码不需要测试" | AI 代码更需要测试：可能存在幻觉 API 和隐含 bug |
| "这只是个原型 / POC" | 原型经常直接上线 |
| "改动太小不值得测试" | 小改动引发的回归 bug 占比最高 |
| "别的模块也没写测试" | 技术债不该继续累积，从现在开始 |
| "跑一下看看就行" | 手动测试不可重复、不可追溯 |

## [HIGH] Simplicity First — 最小可解

- 只写解决当前需求的最少代码
- 禁止预设灵活性 / 配置项 / 未被要求的抽象
- 禁止为不可能发生的场景写错误处理
- 写完自问："资深工程师会不会说这过设计了？"→ 若是则重写
- 单次使用的逻辑禁止抽象成通用工具；出现第 2 次使用时再重构

## [CRITICAL] Surgical Changes — 外科式修改

**铁律：每一行 diff 都必须能追溯到用户明确要求。**

- 只动用户明确要求的部分，禁止"顺手"改邻近代码 / 注释 / 格式
- 匹配已有风格，即使你认为写法不好（改进另开一次提交）
- 发现无关的 dead code / 旧 bug / 风格问题 → **指出但不删**，留给用户决定
- 只清理**本次修改制造**的孤儿（未用的 import / 变量 / 函数）
- 自检：无法追溯到用户要求的改动必须撤回

**为什么是 CRITICAL**：scope creep 是 code review 最大的成本来源——本应 20 行的改动变成 200 行混合改动，
审查者分不清"请求的修改"和"顺手的重构"，返工和讨论成本陡增。

## [CRITICAL] 系统化调试

**铁律：没有根因分析，就不做修复。** 四阶段：根因调查 → 模式分析 → 假设验证 → 实施修复。
**3 次修复尝试失败 → 立即停止，总结已试方法，把问题抛给人类。**
完整流程见 `.claude/skills/systematic-debugging/SKILL.md`。

## [HIGH] Edit / Write 必须先 Read

**铁律：对任何文件调用 Edit / Write 前，必须先 Read，即使你"觉得记得"内容。**

- subagent 启动时上下文是空的 → 必须重新 Read
- 长会话（>50 轮）中文件可能已被外部改动 → 重新 Read
- 同一文件两次编辑之间若夹了其他工具调用（Bash / 网络 / subagent）→ 重新 Read
- Read 失败 → 立即停止并告知用户，禁止猜测内容拼装 Edit

## [HIGH] 提交前本地预检 — 不依赖 hook 兜底

- 提交前先本地跑一次 `.githooks/pre-commit`，前端改动再加 `cd portal && npm run type-check`
- **本仓库没有能自动修格式的工具**（无 eslint / prettier），所以没有 `--fix` 这一步可走
- **格式问题不要逐行手改**，跑工具的自动修复比手动 Edit 便宜一个数量级
- 同一个格式/lint 失败重复 ≥2 次 → 停下来让人类介入，不要在校验循环里打转
- 本仓库无 lint 工具时，在回复里明确说明"未跑预检"

## [CRITICAL] 可执行检查 > 文档规范

**铁律：本仓库的可执行检查（hook / lint / format / CI 脚本）是规则的真源，高于任何文档。**

| 层级 | 载体 |
|---|---|
| **L0** | 本仓库**可执行**检查：`.husky/*` · `.githooks/*` · `commitlint.config.*` · `.eslintrc*` · `checkstyle.xml` · `analysis_options.yaml` · `.pre-commit-config.yaml` · Makefile 目标 · CI workflow |
| L1 | 本仓库 `CLAUDE.md` 内联规则 |
| L2 | `.claude/rules/*.md`（本文件） |
| L3 | `.claude/skills/*/SKILL.md` |

行为要求：

1. 生成代码 / commit 前，先确认与 L0 无冲突
2. L0 与本文件冲突 → **按 L0 执行**，并在输出中标注 `Local rule applied: <path/to/config>`
3. L0 未覆盖的规则，按 L1 → L3 回退

**为什么是 CRITICAL**：可执行检查是硬性拦截。按文档写出的提交可能被本地 hook 秒拒，导致来回重试。

## [HIGH] Token 成本分级响应

**铁律：减 token ≠ 清空上下文。按"上下文损失最小化"优先用最轻的手段。**

| 级别 | 触发条件 | 手段 | 上下文损失 |
|---|---|---|---|
| **L1** | 要读 ≥5 个文件 / 探索量 ≥50K token / 跨目录全局搜索 / 独立审查工作 | 起 subagent（只读探索类优先） | 0（主线索干净） |
| **L2** | 轮次已多 **且** 当前阶段即将收尾 | 建议用户压缩上下文（`/compact`） | 中间推理丢，结论保留 |
| **L3** | 切换到完全不相关的新任务 | 先写交接文件，再清空会话 | 全丢（但必要） |

L1 **不该**用 subagent 的场景（启动开销反而亏）：读 1-2 个已知路径的文件；单目录简单搜索；改完代码后的局部验证。

L1 约束：subagent 的 prompt 必须**自包含**（不能假设主线索上下文已知）；返回**结论摘要**（≤200 字）而非原始数据；
结果必须经主 agent 审核后才能行动。

L3 硬要求——清空前必须把以下内容写入 `.claude/local/<task>/handoff.md`：

```markdown
## 交接清单
- 当前任务：<一句话>
- 已完成：<列表>
- 未完成 / 阻塞：<列表>
- 下一步第一条指令草稿：<复制即用>
- 关键文件路径：<列表>
- 已确认的决策：<列表>
```

| 反模式 | 应该 |
|---|---|
| 主线索里翻 50 个文件找一个符号 | L1：subagent 跑探索，主线索只收摘要 |
| 会话长了就直接清空重开 | L2：先压缩，仍堵塞才 L3 |
| 清空前不写交接 | L3 硬要求：必须先写 handoff.md |
| 任务没完就清空"瘦身" | 先 L1/L2；清空只用于切任务 |

## 成功标准

- 测试通过，新增代码有对应测试
- 无安全漏洞，无硬编码密钥
- 代码可读、可维护
- 每行 diff 都能追溯到用户要求
