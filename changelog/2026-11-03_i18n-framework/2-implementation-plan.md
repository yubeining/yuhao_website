# 实施计划 —— i18n 框架（2026-11-03）

## 三个决定

**1. 语言状态从 MockProvider 里拿出来**

语言是产品行为（跟人走、跟账号走），mock 是待拆的原型层。混在一起，将来删 mock 会把语言一起删掉。
新建 `i18n/I18nProvider.tsx`，`MockProvider` 改为转手借用 —— 25 个页面 import 不用改。

**2. 手选和探测分开存**

- 手选写 `localStorage['mfg.lang.user']`
- 探测结果**不落盘**

否则：用户手选了中文 → 换一台英文系统电脑 → 探测把选择覆盖掉。这类 bug 只在换设备时出现，最难复现。

**3. 闸门用棘轮，不做一次性全量**

585 行文案不可能一次迁完。所以：
- 存量文件列在 `scripts/i18n-allowlist.txt`，先放过
- 新文件或已迁移文件再出现中文 → 直接失败
- 每迁完一个文件从白名单删一行，**只减不增**

## 落地顺序

1. 框架：`lang.ts`（判定）+ `I18nProvider.tsx`（React 出口）+ `main.tsx` 挂载
2. 规范：`docs/i18n/README.md`（规范）、`glossary.md`（术语）、`inventory.md`（清单）
3. 闸门：`scripts/check-i18n-literals.py` + pre-commit 第 8 道
4. 抽取：按批次 —— auth+components → customer → supplier → ops

## 被否决的做法

- **做两套页面**（中英各一份）：改一个 bug 要改两遍，必然漂移。企业级也不这么做。
- **按端口固定语言**（`/supplier` 一定中文）：需求方指出客户不一定是欧洲人，端只决定权限，不决定语言。
- **IP 地理识别**：VPN / 出差会猜错，欧盟客户还有合规说明义务。
- **引入 TMS（Lokalise / Phrase）**：现在只有中英两种语言，上系统是过度设计。先用仓库内的术语表 + 人工审校。

## 风险

- 状态映射被 10+ 个文件共用，直接改成函数会牵动还没迁移的 ops 页面。
  解法：工厂函数 + `@deprecated` 兼容别名，保证只有一份真相，迁完再删别名。
- 带参数的文案（`共 N 单`）如果靠字符串拼接，语序不同的语言会翻车。
  解法：一律用函数，不用 `+` 拼接。
