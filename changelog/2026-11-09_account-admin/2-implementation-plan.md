# 实施计划 —— 运营后台账号管理（2026-11-09）

## 三个对象，三组路径

| 对象 | 表 | 路径 |
|---|---|---|
| 外部用户（客户 / 供应商联系人） | `external_user` | `/ops/users` |
| 组织（公司） | `organization` | `/ops/organizations` |
| 运营账号 | `ops_user` | `/ops/staff` |

没有合成一个 `/ops/accounts`：两类账号来自**物理隔离的两张表**，字段集本来就不同
（运营账号没有 `email_verified_at`）。合成一个 DTO 会让「这一行来自哪张表」在类型层面消失。

## 「删除」= `status = DISABLED`，不加 `is_delete`

需求最初说库里已有 `is_delete`，核对后三张表都没有。要让删除和禁用**真正区分**，
就得加列并给所有查询补过滤条件 —— 登录查账号、刷新重载、列表、供应商目录、邀请校验……
漏一处就是「删了还能登录」。

而 `status` 本来就在登录路径上校验（`AuthService` 里 `status != ACTIVE` 直接拒），
所以用 `status` 表达删除是**零风险**的，代价只是「禁用」和「删除」在数据上是同一个状态，
界面上是两个按钮（禁用 / 启用）。

## 哪些字段不可改，为什么

| 字段 | 为什么锁死 |
|---|---|
| 用户邮箱 | 等于换登录名，且必须同时清 `email_verified_at`；改错会让一个人收不到按邮箱发的凭据 |
| 组织类型 | `CUSTOMER ↔ SUPPLIER ↔ INTERNAL` 等于换受众，端级闸门、权限、可见数据全变 |
| 用户所属公司 | 等于把一个人的历史订单挪到另一家公司名下 —— 那是数据迁移，不是编辑 |

## 校验规则（服务端，不靠前端）

- 外部用户只能挂在 `CUSTOMER` / `SUPPLIER` 组织下（挂 INTERNAL 会让外部账号拿到内部受众）
- 运营账号只能挂在 `INTERNAL` 组织下
- 运营账号的邮箱还要跨表查一次 `external_user`：同一个邮箱既是客户又是运营时，
  「登录走哪条路」会取决于调用哪个端点，这种歧义必须在写入时挡掉
- 初始密码 8–100 位，和客户自助注册同一条规则

## 已知风险（需求方知情并接受）

**任何拿到 OPERATOR token 的人都能创建运营账号** —— 这是提权通道。当前没有 ADMIN 角色
（`role` 表是空的），`/ops/**` 只按路径前缀拦一次。等 ADMIN 角色落地时，`POST /ops/staff`
要一起收口。

## 前端

一页三个 tab（外部用户 / 组织 / 运营账号），共用同一套「搜索 + 表格 + 行内编辑 + 新建卡片」。
文案全部走 `t.ops.accounts.*` —— `scripts/check-i18n-literals.py` 是只减不增的棘轮，
新文件里出现中文字面量会直接让提交闸门失败。

## 被否决的方案

- **加 `is_delete` 列**：需求方最终选了方案 B（见上）
- **把「谁改了谁」记下来**：需求方明确说现在不记录。没有审计表，要记先建表，是独立的一块
- **物理删除**：账号上挂着订单、报价、图纸，物理删会留下孤儿数据
