# 变更记录

每次有意义的工程变更一个文件夹，用于 code review 和事后回溯。

## 结构

```
changelog/
└── {YYYY-MM-DD}_{slug}/
    ├── 1-requirement.md          需求 / 用户原话 / 背景 / 验收标准
    ├── 2-implementation-plan.md  动手前对齐的计划
    └── 3-changelog.md            真实发生的改动
```

**一分支一文件夹**（不是一 commit 一个）。同一功能分多个阶段做，共用一个文件夹，
在 `3-changelog.md` 里按阶段加小节。

日期用变更**启动**日期，不是合并日期。

## 三份文档写什么

### 1-requirement.md
- **原话保留** —— 记录提需求的人的原始表述，不要过度润色。
  半年后你会想知道当时到底是怎么说的。
- **背景** —— 为什么做（业务价值 / 踩了什么坑 / 合规要求 / 客户要求）
- **验收标准** —— 怎么算完成
- **关联** —— 工单号 / 邮件 / 聊天记录链接

### 2-implementation-plan.md
- **动手前**写好并对齐
- 分阶段（必须做 / 应该做 / 可以延后）
- 列出会改的关键文件、风险点、依赖
- **记录被否决的方案和否决理由** ← 这条最值钱。
  半年后有人问"为什么不用 X 方案"，这里有答案，不用重新讨论一遍。

### 3-changelog.md
- **真实发生的改动**，不是计划
- 按类别：安全修复 / 破坏性变更 / Schema / 功能 / 重构
- 部署清单（迁移顺序、开关、配置变更）
- 遗留项（这次没做但值得跟进的）

## 什么算平凡（可以不写）

- 一行 bug 修复，原因显而易见
- 错别字 / 文案调整 / 纯文档改动
- 依赖版本升级
- 纯格式重构
- 纯技术 bug 修复（根因就是代码缺陷，哪怕改了很多处调用点）
- 纯机械重构（改包名、重命名、无行为变更，哪怕 diff 几百个文件）

**判据：光看 diff 会不会对"为什么"留下疑问？**
不会 → 不用写。
需要代码之外的上下文才能理解（合规要求、客户决策、历史事故、分阶段推进）→ 写。

## 必须写的情况

- 跨多个文件的重构
- Schema 变更（新表 / 新列 / 迁移）
- 新端点或新 service 方法
- 安全修复
- 破坏性 API 变更
- 跨模块的技术债治理
