## 1. 四个价 + 一个成本

会话里点名的四个价，加上它们共同的源头（**基准价**，是成本不是价）：

| # | 名字 | 币种 | 谁能看 | 定义 |
|---|---|---|---|---|
| 0 | **基准价** | CNY | 内部 | AI 估的**制造成本**（文档 8）。不是任何一个"价"，是下面三个的源头 |
| 1 | **原价 / 内部底价** | CNY | **仅内部** | "低于这个价我们不接"的线。**客户永远看不到** |
| 2 | **AI 价 / 对客价** | CNY 算 → EUR 报 | 客户 | 报给客户的价 |
| 3 | **客户确认价** | EUR（冻结） | 客户 | 客户点确认的那一版报价，D2 下即合同 |
| 4 | **对供价（目标价）** | CNY | 内部 + 被派到的供应商 | 派单时给供应商的价 |

### 价格链

```
零件(图纸+材料+数量+工艺)
        ↓ AI 估（文档 8，输出 base / range_low / range_high / confidence）
   基准价 = 制造成本(CNY)
        │
        ├─→ × (1 + 议价空间 6.7%) ─────────────────→ ④ 对供价(CNY)
        │
        ├─→ range_high + 成本项 + 最低毛利 ────────→ ① 内部底价(CNY)  ★护栏
        │
        └─→ + 成本项 + 利润率(客户档) ──────────────→ ② 对客价(CNY)
                                                        ↓ × 汇率快照（冻结）
                                                     对客价(EUR)
                                                        ↓ 客户点确认（D2：即合同）
                                                     ③ 客户确认价(EUR，锁死)
```

## 2. ★ 为什么底价必须用悲观端（本文档最重要的一节）

文档 8 §3 说「**高估**是隐蔽的杀手」——那是针对**对供价**说的（给高了白送钱、单悄悄丢了）。

**但在 D10 的顺序下（客户先确认价、再派供应商），对客侧正好反过来：低估才是杀手。**

```
AI 把成本估低 30% → 对客价报低 → 客户点确认 → 合同锁死、改不了
                                  ↓
                        之后才派供应商，实际要价更高
                                  ↓
                        差额全部吃掉我们的毛利（毛利只有 22%）
```

文档 8 §2.3 写得很直白：±30% 的精度**只在"先锁供应商再报客户"下才够用**，因为那样误差会被市场纠正；
切到现在这个顺序，**误差直接落在自己身上**。

**所以：底价用 AI 输出的 `range_high`（悲观成本），不用点估。**

```
底价(CNY) = range_high + Σ成本项 + 最低毛利
```

副作用是好的：AI 越没把握，`range` 越宽，`range_high` 越高，底价自动抬高 —— **不确定性自动转化为保守**，不需要额外规则。

> 对比：**对供价**用点估（`base_price`）算，因为那一侧要的是"供应商愿不愿意接"，不是防亏。
> 两个价用同一个模型的**不同分位**，是有意为之。

## 3. 底价：来源、review 与三道卡口

### 3.1 来源：AI 先算，**每单人工 review** ★推翻 D18

- AI 按 §2 公式给出底价 → **运营逐单 review**（可调整）→ review 通过后才能出对客价。

**被推翻的**：D18「AI 置信度 ≥ 阈值就自动出单，客户提交后几秒报价单就出现」。
现在**每一单在客户看到价格前都要有人过一眼**。

**代价（已知并接受）**：运营工作量随单量线性增长；客户不再秒级拿到报价。

**状态机不受影响**：文档 12 里 `SUBMITTED --QUOTE--> QUOTED` 本来就标的是"运营"触发，与本决策一致，无需改动。

> 文档 8 §5 的「置信度低于阈值转人工」仍然有意义 —— 但现在**所有单都过人工**，
> 置信度的作用从"要不要转人工"降级为"提示运营这单要多看两眼"。

### 3.2 三道卡口（接入文档 12 的守卫）

| # | 卡在哪 | 规则 |
|---|---|---|
| ① | **出对客价**（`QUOTE`） | 对客价 < 底价 → 不允许出单，转人工/审批 |
| ② | **客户还价后重报**（`REJECT` → 再 `QUOTE`） | 同上，重报仍要过底价 |
| ③ | **派单定目标价**（`PUBLISH` / `ASSIGN`） | 目标价高到吃掉毛利（即 目标价 + 成本项 + 最低毛利 > 客户确认价）→ 告警/拦截 |

底价的价值就在第 ③ 道：客户价已锁死，唯一还能守的就是"别以任何价派出去"。

## 4. 币种：内部 CNY，对客 EUR 只在报价那一刻换算并冻结

- **内部一律 CNY** 计算与存储（基准价、底价、对供价、成本项）。
- **EUR 只是换算**，且**只换算一次**：生成 `quote` 的那一刻，把 EUR 金额 + 当时汇率一起**快照**在报价上。

**为什么不能实时换算**：D2 规定报价发出后有效期内价格不能变，文档 1 也写明「报价发出后汇率涨了 → 我们承担」。
若 EUR 每次实时换算，客户看到的价会随汇率漂，合同就锁不住，也违反 C2（历史单据自包含）。

## 5. 对供价（目标价）

```
目标价(CNY) = 基准价(点估) × (1 + 议价空间)      议价空间默认 +6.7%，可配
```

- **我们定价，供应商只能接 / 不接**，不竞价 —— 与 D11「派给能力匹配的几家、先到先得」一致。
- 议价空间可按供应商分档（文档 8 Q19），先统一。
- 落在 `ops_order_part.target_price_cny` 上（派单时确定，随零件走）。

## 6. 数据落点

**粒度：一律按零件行**（零件会拆到多张运营/供应商单，不到行就算不出每张单的钱，报废/返工扣款、部分取消也需要到行）。

### 新增 3 张表

**`quote` —— 对客报价，每次重报一版**（`QUOTED --REJECT--> SUBMITTED` 可来回多次）
```
customer_order_id, version, status(DRAFT|SENT|ACCEPTED|REJECTED|EXPIRED),
valid_until,
fx_rate, fx_snapshot_at,          -- ★ 汇率快照，冻结
margin_tier,                       -- ★ 客户档位快照（C3）
total_cny, total_eur,
issued_by, issued_at
```

**`quote_line` —— 报价行，按零件**
```
quote_id, customer_order_part_id,
unit_price_cny, qty, amount_cny, amount_eur,
floor_price_cny,                   -- ★ 底价快照（当时卡的是哪条线）
cost_breakdown  jsonb              -- ★ 六项成本 + 利润率，快照（C3：半年后要能解释这个价）
```

**`price_estimate` —— AI 估价留档**（文档 8 §8 已设计，此处对齐到零件实例）
```
customer_order_part_id,
base_price_cny, range_low, range_high, confidence,
model_version,                     -- ★ 快照，不引用当前模型
feature_snapshot jsonb,            -- ★ 当时喂进去的特征
estimated_at, estimated_by, fallback_to_manual
```

### 2 处加列
- **`customer_order_part`**：`floor_price_cny`（当前底价）、`price_estimate_id`、`floor_reviewed_by`、`floor_reviewed_at`
- **`ops_order_part`**：`target_price_cny`

### 暂不建
- **`price_feedback`**（标签回流，文档 8 §8）：它记「供应商首次接受价 vs 估价 / 接单耗时」。
  本轮 §7 决定**不做派单兜底**，那条信号链不完整，先不建。
  ⚠ 文档 8 §9 明确说过「采样表要在 Phase 1 就建，这是唯一晚做就补不回来的部分」——**这条提醒保留**。

## 7. ★ 已知敞口（本轮明确不解决）

**派出去没人接 = 成本估低了，而客户价已锁死。本轮决定：先不做兜底。**

- 文档 6 §3.2：切到"客户先确认"之后，派单超时兜底从"应该有"变成"**必须有**"。
- 文档 11 D10 遗留的 **Q13**（五道护栏够不够）**继续悬着**。

即：目前没有自动抬价重派、也没有超时转人工，派不出去的单会**悬着**。
客户已确认，悬着即违约风险。**这是有意识的取舍，不是遗漏。**

补的时候建议方向（未拍板）：超时按步长自动抬目标价重派，**抬到底价为止**，再不行转人工决策。

## 9. 落地清单（"建"的时候照此）

1. **迁移**：新建 `quote` / `quote_line` / `price_estimate`；`customer_order_part` 加 4 列、`ops_order_part` 加 1 列；相应索引（`quote.customer_order_id`、`quote_line.quote_id` 等）。金额一律 `numeric(14,4)`，无外键（§4），裸 uuid + 索引。
2. **报价服务**：估价 → 算底价（`range_high` 口径）→ 运营 review → 生成 `quote`+`quote_line`（冻结汇率/档位/成本明细）→ `QUOTE` 事件。
3. **守卫接入**（文档 12）：`QUOTE`（底价卡 ①②）、`PUBLISH`/`ASSIGN`（底价卡 ③）。
4. **测试**：底价用悲观端的回归（`range_high` 变化 → 底价变化）、低于底价拒绝出单、汇率冻结后重算不漂、重报生成新版本且历史版本不可变。
