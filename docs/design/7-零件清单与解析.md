# 7 — 零件清单格式与自动解析

> 编写日期：2026-08-17 ｜ 状态：设计稿
>
> 真实 RFQ 很少只有一个零件，通常是一张几十行的清单。本文档定义
> **平台自己的清单格式**、**如何解析客户上传的任意格式**、以及**为什么必须有人工确认闸门**。
>
> 依赖：文档 3 §2.1（`spec_template` + `spec jsonb`）、D2（客户点接受＝正式订单）、
> 红线 3（一切锚定图纸版本）。

---

## 1. 为什么这件事的风险高于它看起来的样子

D2 定了「客户点接受 = 正式订单」。这条决策让清单解析从一个便利功能变成**风险点**：

```
清单某行数量解析错一位  →  按错的数量报价  →  客户点接受  →  合同成立
                                                            我们按错的价格履约
```

所以本文档的核心不是"怎么解析得更准"，而是**"解析不准的时候怎么拦住"**。
自动解析负责省力，人工确认负责兜底，两者缺一不可。

## 2. 平台的清单行格式

清单行落库为 `rfq_item` + `part_revision`，字段分三层（延续文档 3 §2.1 的做法）。

### 2.1 必填字段

> ⚠️ **本节已被 [文档 9](./9-客户清单实样与导入映射.md) §3–§4 修订。**
> 下表把「图纸版本」和「材料」列为必填，是在拿到真实客户清单之前定的。
> 实样证明客户的清单里**这两列根本不存在** —— 按下表执行，真实清单一行都进不来。
> 现行规则：导入只卡图号 / 名称 / 数量，其余进「待确认」，报价前补齐并由客户确认。

| 字段 | 列 | 说明 |
|---|---|---|
| 行号 | `line_no` | 客户清单里的原始行号。**报价单必须按同一行号呈现**，否则客户对不上 |
| 客户零件号 | `customer_part_no` | 客户自己的编号，不是我们的内部编号 |
| 图纸版本 | `revision` | ★ **不允许为空**。空即错误，必须退回客户补充（红线 3） |
| 零件名称 | `name` | |
| 数量 | `qty` | |
| 材料 | `material_code` | **归一化后的平台代码**，不是客户写的原文 |

### 2.2 常用字段（提成真实列，便于索引与统计）

表面处理、热处理、关键公差、重量、交期要求、备注、关联图纸文件。

### 2.3 长尾字段

进 `spec jsonb`，按品类模板（`spec_template`）走。车铣 / 钣金 / 压铸各有各的字段，
**不要为它们建列**。

### 2.4 ★ 原文与归一化值必须都存

```sql
rfq_item
  material_code      text     -- 归一化：SS-304
  material_raw       text     -- 客户原文：1.4301
  qty                numeric  -- 归一化：1200
  qty_raw            text     -- 客户原文：1.200
  ...
```

**归一化错了要能回溯客户原本写的是什么。**只存归一化结果，出争议时无法自证。

## 3. 最高杠杆的一步：先给模板

在客户提交询价的界面提供**可下载的标准 Excel 模板**。

- 愿意用模板的客户能覆盖大部分量，解析准确率接近 100%
- 不肯改流程的大客户，才走通用解析

**不要反过来做**——先造万能解析器，永远做不完。模板是产品动作，解析是兜底能力。

---

## 4. 解析流程

```
上传 → 定位表头行 → 列映射 → 逐行解析归一化 → 校验分级 → 匹配图纸 → ★确认闸门 → 落库
```

### 4.1 定位表头行

表头**很少在第一行**。前面常有客户 logo、公司抬头、询价编号、日期。
按"哪一行的单元格最像字段名"来判定，不能写死行号。

### 4.2 列映射：按客户记忆

**这是准确率的最大来源。**同一个客户每次发的格式都一样：

```
column_mapping_template
  id, party_id, name, version
  mapping jsonb    -- {"Teile-Nr.": "customer_part_no", "Menge": "qty", ...}
  header_row int, locale text, status
```

第一次人工确认映射关系，之后自动套用，并在界面标明"已套用你上次的对应关系"。
比任何智能识别都管用。

### 4.3 校验分级 —— 三档，不是两档

| 级别 | 含义 | 客户能否提交 | 能否进入寻源 |
|---|---|---|---|
| **正常** | 解析无歧义 | ✅ | ✅ |
| **需注意** | 解析出结果，但需要人确认判断 | ✅ | ❌ **必须先处置** |
| **必须处理** | 无法得出可用值 | ❌ **阻断** | ❌ |

**两道闸门，位置不同**：

- **客户侧**：错误清零才能提交。警告可以带着提交（我们会处理），否则客户被卡在
  他判断不了的问题上（例如"这个橡胶件你们做不做"）。
- **内部侧**：警告也必须处置完，才能生成寻源包。**清单错一行，报价就是错的。**

## 5. 欧洲客户清单里的七个坑

这一节是具体的、会真实发生的。

### 5.1 ★ 德语 Excel 的小数逗号

`1.234,56` 在德语区是 **1234.56**，不是 1.234。

`1.200` 到底是 **1200** 还是 **1.2**？——**无法从数值本身判断**，必须结合：
- 客户所属地区的数字格式（`party.locale`）
- 同列其他值的模式
- 仍然不确定 → **判为"必须处理"，让人来定**

猜错就是 1000 倍的量差。**这一条是本文档里最贵的一行。**

### 5.2 材料别名

`1.4301` = `X5CrNi18-10` = `AISI 304` = `SUS304`，是同一种钢。

必须建材料归一化对照表，这是**平台能长期积累的真资产**：

| 德标编号 | 德标牌号 | 等同牌号 | 平台代码 |
|---|---|---|---|
| 3.3211 | AlMgSi1 | 6061 系 | AL-6061 |
| 1.4301 | X5CrNi18-10 | AISI 304 / SUS304 | SS-304 |
| 1.4404 | X2CrNiMo17-12-2 | AISI 316L | SS-316L |
| 1.4305 | X8CrNiS18-9 | AISI 303 | SS-303 |
| 42CrMo4 | 42CrMo | AISI 4140 | AS-42CRMO |

命中对照表 → 标"需注意"让人确认一次（等同牌号在性能上并不完全相等）；
命中不了 → "必须处理"。

### 5.3 数量列有好几个

年用量 / 本次订货量 / 批量 / 最小包装量，德语里是
`Jahresbedarf` / `Bestellmenge` / `Losgröße` / `VPE`。

**选错列，报价差几倍。**列映射必须明确指定哪一列是本次询价数量。

### 5.4 单位

- 长度：mm / inch
- 重量：kg / g
- 计量单位：`Stück`（件）vs `Satz`（套）—— **一套里含几件？**必须问清楚

### 5.5 合并单元格

同一个零件号跨多行（不同工序、不同表面处理）。解析时要向下填充，
否则第 2、3 行的零件号是空的。

### 5.6 小计行 / 合计行 / 空行

混在明细里。不过滤会多出垃圾数据行，而且金额列的合计值会被当成某个零件的数量。

### 5.7 表头是双行的

上面一行合并单元格写"尺寸"，下面一行写"长/宽/高"。按单行找表头会失败。

## 6. 图纸文件与清单行的匹配

清单 30 行，客户传了 28 个 STEP 文件 —— **哪个文件对哪一行**，本身是个匹配问题。

> ⚠️ **本节的匹配假设已被 [文档 9](./9-客户清单实样与导入映射.md) §4.3 扩充。**
> 实样里文件名有五种风格，其中 51 个文件是**纯数字 ID**，不含零件号原文，
> 单靠下面的正则匹配不到。实际还要先按目录归集、再做数字 ID 还原。

**做法**：按文件名里的零件号 + 版本号做正则匹配。同一个零件号的写法有多种：

```
HV-220-004_A.step     HV-220-004 A.step     HV-220-004-A.step
HV-220-004_RevA.step  HV-220-004(A).step
```

匹配不上的，在确认界面里**手工拖拽关联**。

**任何一行没有关联到图纸文件，不允许进入寻源。**（红线 3：没有图纸版本就没有锚点）

## 7. ★ 解析记录必须快照

和 C3（历史单据自包含）是同一条原则：

```sql
bom_import
  id, rfq_id, party_id
  source_file_id       uuid      -- 原始文件本身
  sheet_name, header_row, locale
  mapping_template_id  uuid
  mapping_snapshot     jsonb     -- ★ 当时用的列映射，不是引用当前模板
  parsed_result        jsonb     -- ★ 当时的解析结果
  parsed_at, parsed_by
  confirmed_at, confirmed_by     -- 谁确认的、什么时候
```

**为什么**：半年后客户说"我当时写的是 1200"，你要能拉出
原始文件 + 当时的列映射 + 当时的解析结果。
如果 `mapping_snapshot` 是外键引用 `column_mapping_template`，
而模板后来改过，这份历史记录就被篡改了 —— 和参考系统里"审批表单 join live 模板"
是同一个事故。

**确认动作也要留痕**：谁确认的、确认的是哪一版解析结果。这是 D2 下的责任凭据。

---

## 8. 对现有设计的影响

| 影响面 | 说明 |
|---|---|
| `rfq_item` | 增加 `line_no` / `*_raw` 原文字段 |
| 新增表 | `bom_import`、`column_mapping_template`、`material_alias` |
| 报价单 | **必须按客户原始行号呈现**，否则客户对不上 |
| 寻源包 | 按行下发；**行号要脱敏**（客户的行号会泄露他的产品结构） |
| 路线图 | 建议进 Phase 1 —— 没有它，Phase 1 的"在线提交询价"只能处理单零件，跑不了真实生意 |
