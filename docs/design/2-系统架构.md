# 2 — 系统架构

## 1. 部署单元切分

**四个部署单元，一个后端。**

| 单元 | 内容 | 技术 | 域名 | 何时上 |
|---|---|---|---|---|
| `site` | 公司官网：公司介绍 / 设备产能 / 工艺能力 / 质量认证 / 案例（脱敏）/ 联系我们 / Request a Quote | Next.js **SSG**，多语言 | `www.xxx.com` | Phase 0 |
| `portal` | 客户端 + 供应商端 + 内部后台，三个 route group | Next.js App Router，全部登录态 | `app.xxx.com` | Phase 1 |
| `backend` | 唯一后端，`/api/v1` 前缀 | Spring Boot 3.5 / Java 21 | `api.xxx.com` | Phase 1 |
| `cad-worker` | CAD 转换 / 图纸脱敏 / 加水印 / 转 PDF 预览 | 独立容器，仅内网可达 | — | Phase 2 |

### 1.1 为什么官网必须独立且用 SSG

欧洲客户是 Google 搜 `CNC machining China supplier` / `Lohnfertigung Zerspanung` 找过来的。
SEO 是获客命根子，需要：静态渲染、`hreflang` 多语言、Schema.org 结构化数据、Core Web Vitals 达标。
塞进登录态 SPA 里会毁掉这些。

官网和平台唯一的连接点：**Request a Quote 表单 → 创建 Lead → 落进后台**。
官网本身不需要数据库，内容用 MDX 或轻量 CMS 管理，让市场同事能自己改。

**顺带一条**：官网的 canonical URL、sitemap、JSON-LD 里的链接必须是真实规范链接，
不要用短链或跳转 —— 爬虫会索引重定向而不是页面。

### 1.2 为什么三个门户不拆成三个 App

小团队维护成本翻三倍，而**真正的安全边界在后端，不在前端 bundle**。
三个 route group + middleware 按身份类型硬闸门就够。

但要接受一条硬规则：
> **前端代码里绝不允许出现"根据角色隐藏字段"的逻辑。**
> 供应商端拿到的 JSON 里从一开始就不该有客户名和对客价。

**将来必须拆分的触发条件（写死，别临时讨论）**：
① 出现要求数据不出欧盟的客户 → 客户端 + 存储要 EU region
② 供应商端需要独立的发布节奏或独立域名备案

### 1.3 为什么 CAD 转换必须是 sidecar

STEP 文件几十到几百 MB，转换过程吃内存以 GB 计，还可能挂死。
跑在 backend 进程里，一个大文件就能把整个 API 拖垮。

必须是独立容器：backend 只负责下发任务和取回结果，转换服务可以单独扩缩容、单独限流、
单独设超时。同时它是唯一需要装 CAD 库（OpenCascade 之类）的镜像，
不该污染 backend 的镜像体积。

## 2. 后端包结构

```
com.<company>.mfg/
├── MfgApplication.java
├── common/                    # 跨领域基础设施 —— 原样借鉴 WeAct
│   ├── dto/                   # ApiResponse<T>, PagedResponse<T>
│   ├── exception/             # BusinessException, GlobalExceptionHandler
│   ├── security/              # JwtTokenProvider, JwtAuthFilter, UserPrincipal,
│   │                          # @CurrentUser, @CurrentParty, PortalGuardInterceptor
│   ├── cache/                 # CacheKeys（集中管理 key，禁止手写拼接）
│   ├── interceptor/           # ResponseWrapperAdvice
│   └── service/               # RedisService
├── config/                    # @Configuration
├── platform/                  # 平台与基础设施（无业务语义）
│   ├── party/                 # 交易方 + 用户（客户公司 / 供应商 / 我们）
│   ├── auth/                  # 三端三套登录方式，统一出口
│   ├── access/                # 路由表 + 端级闸门 + ops 端 RBAC
│   ├── file/                  # 文件对象、直传、签名 URL、病毒扫描
│   ├── notification/          # 邮件 / 微信 / 企微，channel adapter
│   ├── audit/                 # 审计事件
│   ├── i18n/                  # 文案 code 注册表（后端只返 code）
│   ├── fx/                    # 汇率获取 + 快照
│   └── dbmigration/           # 开机自动应用 migration
├── domain/                    # 业务核心
│   ├── lead/                  # 官网线索
│   ├── rfq/                   # 询价单（客户侧）
│   ├── part/                  # 零件 + 图纸版本 + 规格模板
│   ├── sourcing/              # 寻源包 + 供应商邀请 + 供应商报价
│   ├── pricing/               # 定价规则 + 计算引擎
│   ├── quote/                 # 对客报价（含审批）
│   ├── order/                 # 订单
│   ├── production/            # 生产订单 + 里程碑
│   ├── qc/                    # 质检
│   ├── shipment/              # 发货 + 包装 + 物流跟踪
│   ├── document/              # 单据（PI / 装箱单 / 材质证明 / 报关资料）
│   ├── supplier/              # 供应商能力库 + 表现记录
│   └── settlement/            # 账款状态（只记录，不收款）
└── ops/                       # 内部后台专用的聚合查询 / 看板 / 报表
```

**说明**：WeAct 用了 `platform / module / appcenter` 三分包，那是因为它是"工作区 + 多 app"形态。
你这是**单一业务流的垂直系统**，简化成 `platform / domain` 两分包即可。

**域内固定四层**：`controller/ service/ repository/ dto/`。
单文件域保持扁平。定时任务 / 外部适配器 / 数据回填一律进 `service/`，不另开 `scheduler/` `adapter/` 目录。

**明确不用 DDD 分层**（`api/application/domain/infrastructure`）—— 这个系统 CRUD 为主，
真正有领域逻辑的只有定价引擎一个模块，为它套全局 DDD 是过度设计。

## 3. 身份与隔离模型 ★核心设计

### 3.1 Party 模型

```sql
party
  id          uuid pk
  type        enum { CUSTOMER, SUPPLIER, OPERATOR }
  code        text unique          -- 内部编码，如 C-0012 / S-003
  name        text
  country     text
  status      enum { ACTIVE, SUSPENDED }
  ...

party_user
  id          uuid pk
  party_id    uuid fk
  email       text
  phone       text
  role        text                 -- 各端内部角色
  status      enum
  ...
```

`OPERATOR` 是单例（或少数几个法人主体）。
所有归属于某个交易方的数据行都带 `party_id`。

### 3.2 投影分离 —— 不要让三端共用同一实体的读路径

**问题**：一个 RFQ 要被客户、后台、供应商看到，内容完全不同。
"同一实体按角色过滤字段"这种做法，漏一个字段就是泄露。

**解法**：把面向供应商的对象**物理上分离出来**。

```
Rfq / RfqItem                    客户侧真相
                                 含：客户身份、联系人、目标价、终端用途、交付地址
      │
      │  后台执行「下发寻源」动作，生成 ↓
      ▼
SourcingPackage / SourcingItem   发给供应商的匿名包（独立的表）
                                 只含：脱敏图纸版本 + 材料 + 工艺 + 公差 +
                                       表面处理 + 数量 + 交期窗口 + 技术要求
                                 不含：客户名/国家/联系人/目标价/对客价/其他供应商
      ▼
SupplierQuote                    供应商成本（CNY）
      ▼
CustomerQuote / QuoteLine        后台合成的对客报价（EUR）+ 定价分解快照
```

这样**供应商端的所有查询根本碰不到 `rfq` 表**，泄露在数据层就不可能发生，
而不是靠"记得过滤"。

### 3.3 端级硬闸门 —— 路径前缀即受众

```
/api/v1/customer/**    仅 CUSTOMER 类型 principal
/api/v1/supplier/**    仅 SUPPLIER 类型 principal
/api/v1/ops/**         仅 OPERATOR 类型 principal
/api/v1/public/**      无鉴权（官网表单、公开报价查看链接）
```

`PortalGuardInterceptor` 作为**第一道拦截器**，按 principal type 直接拒。
这比细粒度资源 key 更粗，但对这个系统更安全 —— 跨端泄露是头号风险。

细粒度权限只在 **ops 端内部**需要：销售 / 采购 / 质检 / 物流 / 财务 / 管理员。
用「路由表 → 资源 key + 拦截器」的零注解方案（借鉴 WeAct 的 `RouteAccessRegistry`）：
新增端点只需在路由表加一行，不碰任何 controller。

客户端和供应商端的角色简单到不需要引擎：管理员 / 成员，两个够了。

> **不要一上来就上 Casbin。** 先用一张 `(user_id, resource_key, action)` 表 +
> 同样的拦截器接口，业务代码不感知实现。将来真需要策略引擎再换，业务代码不动。

### 3.4 数据隔离的六条铁律

1. **Service 写方法必须显式接收 `partyId`**，不许从查出来的实体反推，不许在 service 内部从 principal 默认取。
2. **交易方范围的查询必须 `findByIdAndPartyId(id, partyId)`**。裸 `findById` 出现在业务代码里就是红旗。
3. **DTO 禁止接受客户端可控的身份和定价字段**：`partyId` / `customerId` / `supplierId` / `unitPrice` / `createdBy` 一律服务端推导。
4. **供应商端 response DTO 必须白名单序列化** —— 只允许显式列出的字段，默认不暴露。命名统一 `SupplierXxxView`，code review 必查。
5. **公开端点（无 JWT）的范围从资源反查**，绝不信客户端传的 party。
6. **任何文件访问都要过一次「这个 principal 对这个 revision 有权」的显式校验 + 审计落库**。

## 4. 三端认证

三种受众的现实条件完全不同，不要强求统一登录方式：

| 端 | 方式 | 理由 |
|---|---|---|
| 客户（欧洲） | **邮箱 + 验证码（OTP）**；密码作为并行通道保留。【2026-11-02 需求方拍板】 | 客户在欧洲，邮箱是唯一稳定的身份载体；验证码免去"记密码 + 找回密码"这一整条链路。密码保留是为了可回退、老账号不受影响。原先写的「邮箱 + 密码」是 2026-09-09 的方案，已被本轮取代。⚠ 原有约束不变：注册即可用、无人工审核、同一组织内不分角色 |
| 供应商（中国） | 手机号 + 验证码，邀请制开户 | 个位数供应商，管理员开户最省事；手机号登录在车间最实用。**★ 短信通道尚未实现**（2026-11-02 只有邮箱通道），所以供应商当前仍用密码登录；`POST /auth/otp/send` 传 `SMS` 会明确返回 `auth.otp_channel_unavailable`，不要当成可用 |
| 内部 | 企业微信/钉钉扫码，或邮箱密码 | 跟现有办公工具打通 |

**验证码登录的落地形态（2026-11-02）**：`POST /auth/otp/send` → `POST /auth/otp/verify`。
校验通过后走**同一个签发出口**（`AuthTokenIssuer` → 同一个 `TokenResponse`），
和密码登录没有第二套发 token 的逻辑。**未注册的邮箱验证通过后不建号、不发 token**，
返回 `registrationRequired=true` —— 建号需要公司信息，那一步还没做。

**但三条路径必须汇入同一个出口**（借鉴 WeAct 的 `IdentityExchanger` 模式）：
每种登录方式实现一个 exchanger，产出统一的 `AuthContext`，
交给唯一的 `AuthService.provisionAndIssueToken()`。

**为什么重要**：将来加登录方式（比如客户要求 SSO），只加一个 exchanger，
不用在三处重复实现"建用户 / 绑 party / 发 token / 记登录审计"的逻辑。
WeAct 的教训是：一旦某个 provider 的路径单独实现了一半，两条路径就会永久性地不一致。

## 5. 文件与图纸处理 ★风险最高的模块

### 5.1 直传对象存储，后端绝不碰字节

STEP 文件几十到几百 MB。走「后端申请签名上传 URL → 浏览器直传对象存储 → 回调完成」：

```
① POST /customer/files/initiate  { fileName, size, mimeType, purpose }
     后端校验：类型白名单、大小上限、配额
     后端生成对象名（UUID，绝不用客户传的文件名做路径）
     返回 { fileId, uploadUrl }（resumable session 或 signed PUT）
② 浏览器直传对象存储
③ POST /customer/files/{fileId}/complete
     后端 HEAD 校验：实际大小、实际 Content-Type、magic bytes
     入库，触发异步处理（病毒扫描 / 预览生成）
```

**五条信任边界**（缺一不可）：
① 两端都做 party 范围校验 ② 对象名服务端生成 ③ complete 时重新校验 MIME
④ complete 时重新校验大小 ⑤ ~~存储桶 CORS 白名单是具体域名，不是 `*`~~ **（Sealos 上做不到，已接受全放行，见下方说明）**

> ★ **2026-09-11 实测：⑤ 在 Sealos 上做不到，已接受全放行。**
>
> - 存储服务对**任意来源**的跨域预检都原样放行（`Origin: https://evil.example` 也回 204）。
> - 查询桶 CORS 回 `NoSuchCORSConfiguration`；设置桶 CORS 试了两次（带 / 不带 S3 命名空间）都回 `400 MalformedXML`，之后外部来源仍被放行，配置没有改变。
> - 线上存储是 MinIO（`/minio/health/live` 返回 200）。MinIO 社区版源码里桶级 CORS 的查询 / 设置 / 删除都是空壳处理器，真正的实现（minio/minio PR #20150）没有合进社区版。
>   返回 `MalformedXML` 而不是 `NotImplemented` 的具体原因**没有核实**（推测：这版 MinIO 没有这条路由，请求被当成建桶来解析）。
> - 全局 CORS 开关在 Sealos 平台手里，我们改不了。
> - **为什么可以接受**：桶是私有的，所有访问都靠 15 分钟有效的签名 URL。CORS 只管浏览器里的网页能不能读到响应，拿到签名 URL 的人用 curl 照样能下载，这一层 CORS 本来就挡不住。
> - 浏览器直传不需要任何额外配置。真要收紧，只能找 Sealos 改平台的全局配置。


### 5.2 文件类型校验不信扩展名

按 magic bytes 判断真实类型。允许清单：
`STEP/STP`、`IGES/IGS`、`X_T`（Parasolid）、`SLDPRT`、`DWG`、`DXF`、`PDF`、`ZIP`（打包图纸）、常见图片。

ZIP 要解开检查内层类型和解压炸弹（压缩比 + 总大小上限 + 嵌套层数上限）。

### 5.3 图纸版本化

```
part           零件（客户侧的逻辑零件，可能跨 RFQ 复用）
part_revision  版本（rev_code: A/B/C…，每版一套文件）
part_file      具体文件（original / sanitized / preview / watermarked）
```

- 报价、订单、生产、质检、发货**全部外键到 `part_revision_id`**
- 客户上传新版本 → 系统标记受影响的报价/订单 → **强制一次人工决策**：
  「是否重新报价 / 是否影响在产订单」，不允许静默继承
- 已进入生产的 revision **禁止删除**

### 5.4 脱敏是一道显式工序

客户图纸标题栏通常带客户 logo、公司名、零件号、项目代号，直接转发等于告诉供应商客户是谁。

| 阶段 | 做法 |
|---|---|
| MVP | **后台人工上传一份脱敏版**。系统强制：没有 `sanitized` 版本，「下发寻源」按钮点不动 |
| Phase 2 | `cad-worker` 自动处理：标题栏遮盖 + 文件元数据清洗（作者/公司/路径） |

**下发给供应商的每份图纸打不可见水印**（供应商 ID + 下发批次 + 时间戳），泄露可溯源。
这一条对个位数长期供应商尤其有价值 —— 它不是防外人，是让内部人知道有追溯。

### 5.5 图纸访问全审计

每一次访问落库：`谁 / 何时 / 哪个 revision / 哪个文件 / 从哪个 IP / 什么用途`。

这**不是"以后加"的功能**，是跟欧洲客户签保密协议时的交付物 —— 客户会问
"如果我的图纸泄露了，你们能查到是谁看过吗"。要能一键导出某个 revision 的完整访问记录。

签名 URL 有效期设短（5–15 分钟），且**每次生成签名 URL 就是一次访问事件**。

### 5.6 存储位置可配置

D1 定了单区，但存储桶所在区、URL 生成、数据库连接全部走配置，
业务代码里不出现任何区域相关的常量。将来拆欧洲区时才有可能不重写业务代码。

## 6. 通知

| 收件方 | 主通道 | 备通道 |
|---|---|---|
| 客户（欧洲） | 邮件 | 站内消息中心 |
| 供应商（中国） | **微信 / 企业微信** | 短信、邮件 |
| 内部 | 企业微信 / 钉钉 | 邮件 |

统一抽象 `NotificationService` + 每个通道一个 adapter。
**供应商侧的微信通知是采纳率的关键**，不是可选项 —— 只发邮件的话他们不会看。

关键通知点：RFQ 提交、寻源包下发、报价即将过期、报价发出、客户接受/拒绝、
生产订单下达、里程碑逾期、质检结果、发货、物流异常。

## 7. 其他非功能项

| 项 | 要求 |
|---|---|
| **时区** | 全部 UTC 存储（`timestamp with time zone`），按 viewer 时区渲染。欧洲客户和中国供应商看同一个交期，不能差 6-7 小时 |
| **多语言** | 后端**只返 code 不返文案**，翻译全在前端。官网 EN + DE；客户端 EN（DE 加分）；供应商端 + ops 端中文 |
| **GDPR** | 客户联系人是个人数据。需要：官网 cookie consent、隐私政策、删除权 / 导出权、数据处理记录。**欧洲客户第一轮尽调就会问** |
| **出口管制** | 航空航天 / 军工相关零件有双用途管制。至少要有标记字段 + 人工复核闸门 |
| **NDA 追溯** | 供应商访问图纸前必须有 NDA 记录；访问日志可导出 |
| **搜索** | Postgres 全文检索够用，别上 Elasticsearch |
| **定时任务** | 每个 `@Scheduled` 必须按条目加 Redis 锁（`SET NX EX` + UUID fence + `finally` 释放），DB 层有唯一索引兜底。多 pod 下不加锁 = 重复通知 / 重复下发 |
