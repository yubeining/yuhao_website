# 3 — 领域模型与核心流程

## 1. 实体全景

```
Lead                        官网线索
  └─▶ Rfq ──┬─ RfqItem ──▶ PartRevision ──▶ PartFile{original|sanitized|preview|watermarked}
            └─ RfqAttachment              （技术要求 / 检验标准 / 3D 模型）

Rfq ──▶ SourcingPackage ──┬─ SourcingItem
                          └─ SupplierInvitation ──▶ SupplierQuote ──▶ SupplierQuoteLine

Rfq ──▶ CustomerQuote (版本化 + 有效期 + 审批) ──▶ CustomerQuoteLine (含定价分解快照)

CustomerQuote ──客户接受──▶ Order ──┬─ OrderLine
                                    ├─ ProductionOrder (按供应商) ──┬─ ProductionOrderItem ★拆分点
                                    │                                └─ Milestone
                                    ├─ QcInspection ──▶ QcDefect / QcReport
                                    ├─ Shipment ──▶ Carton ──▶ TrackingEvent
                                    ├─ Document (PI / 装箱单 / 材质证明 / CoC / 报关)
                                    └─ SettlementRecord (仅状态)

Supplier ──▶ SupplierCapability   设备 / 工艺 / 材料 / 尺寸范围 / 产能
        ──▶ SupplierPerformance   合格率 / 准时率 / 响应速度 / 历史单量（记录，不做算法）
```

## 2. 关键表设计要点

### 2.1 零件规格用 jsonb + 规格模板

非标定制的规格维度是发散的（车铣 / 钣金 / 压铸 / 注塑 各有各的字段），
**不要建 200 个列**。

```sql
spec_template            -- 按品类定义字段（字段名/类型/单位/必填/可选值）
  id, category, name, schema jsonb, version, status

part_revision
  ...
  spec_template_id  uuid
  spec              jsonb   -- @JdbcTypeCode(SqlTypes.JSON) + columnDefinition = "jsonb"
```

常用字段（材料、数量、公差等级、表面处理、热处理、交期）可以提成真实列方便索引和统计，
长尾字段进 jsonb。

### 2.2 报价行必须存全量分解快照

```sql
customer_quote_line
  id, quote_id, rfq_item_id, part_revision_id
  qty                     int
  unit_price_eur          numeric(14,4)
  total_eur               numeric(14,2)
  -- ★ 快照区，全部是"当时"的值，绝不 join live 配置
  pricing_rule_version    text
  fx_rate                 numeric(12,6)      -- CNY→EUR
  fx_buffer_pct           numeric(6,4)
  fx_snapshot_at          timestamptz
  incoterm                text               -- EXW / FOB / CIF / DAP / DDP
  cost_breakdown          jsonb              -- 每一项费用的金额和来源
  supplier_quote_line_id  uuid               -- 选用了哪家的报价
```

`cost_breakdown` 长这样：

```json
{
  "supplierCost":      { "amountCny": 12800.00, "supplierQuoteLineId": "..." },
  "toolingAmortized":  { "amountCny": 1500.00, "ruleRef": "TOOLING_AMORT_v3" },
  "qcCost":            { "amountCny": 320.00,  "ruleRef": "QC_STD_v2" },
  "packaging":         { "amountCny": 450.00 },
  "domesticFreight":   { "amountCny": 600.00 },
  "exportFees":        { "amountCny": 800.00 },
  "intlFreight":       { "amountCny": 3200.00, "ruleRef": "SEA_EU_W_v5", "chargeableWeightKg": 128 },
  "duty":              { "amountCny": 1900.00, "hsCode": "8466.93", "destCountry": "DE", "ratePct": 2.7 },
  "marginPct":         { "value": 0.22, "ruleRef": "MARGIN_TIER_B_v4" }
}
```

> **这条是从 WeAct 一系列事故里直接吸取的**：审批表单 join live 模板导致历史被篡改、
> OKR 修订行 overlay 导致数字对不上。**历史单据必须自包含。**

### 2.3 定价规则是数据不是代码

```sql
pricing_rule
  id, code, version, category, effective_from, effective_to, status
  applies_to_incoterms  text[]     -- 该费用项在哪些贸易条款下计入 ★
  formula               jsonb      -- 分档表 / 系数 / 常量
```

`applies_to_incoterms` 解决了「价格口径还没定」的问题：
国际运费和关税这两项标注 `{DAP, DDP}`，EXW/FOB 下自动不计入。
将来贸易条款定了，改配置不改代码。

**改毛利率不需要发版**，改运费档不需要发版。

### 2.4 拆单不变式 ★D3 的落地

```sql
order_line
  id, order_id, part_revision_id, qty, unit_price_eur, ...

production_order                    -- 一个供应商一个
  id, order_id, supplier_party_id, status, issued_at, due_date, ...

production_order_item               -- ★ 拆分点：一个订单行可对多个生产订单
  id, production_order_id, order_line_id, qty, unit_cost_cny
```

**核心不变式**：

```
∀ order_line L :  Σ(production_order_item.qty WHERE order_line_id = L.id)  ≤  L.qty
```

必须三层同时守：
1. **DB 层**：触发器或每次分配后校验（PostgreSQL 用 `CHECK` 表达不了跨行聚合，用触发器）
2. **Service 层**：分配时在同一事务内 `SELECT ... FOR UPDATE` 订单行再校验
3. **集成测试**：并发分配 + 超额分配 + 部分分配后取消，三个 case 必须有

**必须有"未分配数量"视图**，采购看板上直接显示，否则一定会漏分。

### 2.5 QC 挂在生产订单明细上

不同供应商做的同一零件，质量是分开判的：

```sql
qc_inspection
  id, production_order_item_id, ★    -- 不是 order_line_id
  inspected_qty, passed_qty, failed_qty
  result enum { PASSED, PARTIAL, FAILED }
  inspector_user_id, inspected_at, report_file_id
```

发货可以合并（一个 shipment 装多个供应商的货），所以 `shipment` 和 `production_order` 是多对多，
通过 `shipment_item` 关联到 `production_order_item`。

## 3. 状态机

### RFQ（询价单）
```
DRAFT ──▶ SUBMITTED ──▶ UNDER_REVIEW ──▶ SOURCING ──▶ QUOTED ──┬─▶ WON
                             │                                  ├─▶ LOST
                             ├─▶ NEED_INFO (退回客户补资料)       └─▶ EXPIRED
                             └─▶ DECLINED (我们不接)
```

### SupplierQuote（供应商报价）
```
INVITED ──▶ VIEWED ──▶ SUBMITTED ──┬─▶ SELECTED
                          │         └─▶ NOT_SELECTED
                          └─▶ EXPIRED
DECLINED（供应商明确不报）
```

### CustomerQuote（对客报价）★最关键
```
DRAFT ──▶ PENDING_APPROVAL ──▶ APPROVED ──▶ SENT ──┬─▶ ACCEPTED  → 生成 Order
                    │                        │      ├─▶ REJECTED
                    └─▶ REJECTED(内部驳回)     │      ├─▶ EXPIRED（到期自动）
                                              └──────┴─▶ WITHDRAWN（客户接受前撤回）
```

### Order（订单）
```
CONFIRMED ──▶ IN_PRODUCTION ──▶ QC ──▶ PACKED ──▶ SHIPPED ──▶ DELIVERED ──▶ CLOSED
                                 └─▶ QC_FAILED ──▶ (MVP: 人工处理) ──▶ 回到 IN_PRODUCTION
                    CANCELLED（各阶段可取消，需理由 + 审批）
```

### ProductionOrder（生产订单）
```
ISSUED ──▶ ACCEPTED ──▶ IN_PROGRESS ──▶ SUBMITTED_FOR_QC ──▶ DONE
   │                                            └─▶ REWORK ──▶ IN_PROGRESS
   └─▶ REJECTED（供应商拒接，需理由）
```

> **状态流转必须有自己的审计动词**：`order.status_change`，
> 不要用 `order.update` + `status=xxx` 混在字段更新里。查问题时天差地别。

## 4. ★ 报价五道护栏（D2 的落地）

因为「客户点接受 = 正式订单」，报价在法律上是**要约**。以下五条是强制的，不是可选的。

### 护栏 1 — 报价强制有效期

```sql
customer_quote
  valid_until  timestamptz NOT NULL   -- 不允许为空
```

- 创建时必填，默认 15 天（可配）
- 定时任务扫描过期 → 自动转 `EXPIRED`（**加 Redis 锁**）
- **客户端接受接口第一件事就是校验 `now() < valid_until`**，过期直接 409
- 过期报价在客户端展示为灰态，接受按钮不可点（但后端校验才是真的防线）

### 护栏 2 — 发出前必须内部审批

```
DRAFT → PENDING_APPROVAL → APPROVED → SENT
```

审批规则可配置，建议起步规则：
- 单笔金额 < X 万欧：销售负责人单人审批
- 单笔金额 ≥ X 万欧 **或** 毛利率 < Y%：需要第二人（总经理/财务）复核
- 毛利率为负：**硬阻断**，不允许提交审批

审批记录不可篡改，含审批人、时间、当时看到的金额和毛利率。

### 护栏 3 — 供应商报价有效期必须覆盖对客报价有效期

```
supplier_quote.valid_until  ≥  customer_quote.valid_until
```

**发出报价时系统强制校验**，不满足则阻断并提示"XX 供应商的报价 X 月 X 日过期，
早于对客报价有效期，请先延长供应商报价有效期或缩短对客有效期"。

这一条防的是最典型的坑：对客报了 30 天有效期，供应商报价只保 7 天，
第 20 天客户接受了，供应商说"那个价早过期了，现在要涨 15%"。

### 护栏 4 — 汇率快照 + buffer

- 报价生成时锁定汇率，写进每一行的快照
- 加一个可配的 buffer（建议 2–3%），吸收有效期内的汇率波动
- 汇率来源和取值时间一并记录
- 有效期越长，buffer 应该越大 —— 做成"有效期天数 → buffer%"的分档表

### 护栏 5 — 客户接受前可撤回，且留痕

`SENT → WITHDRAWN` 允许，但：
- 必须填理由
- 必须通知客户（撤回一份已发出的报价对商誉有损，要让操作者意识到）
- 全量留痕

**并发问题（必须处理）**：客户点"接受"和后台点"撤回"可能同时发生。
用**乐观锁 + 状态机原子转换**：`UPDATE customer_quote SET status='ACCEPTED'
WHERE id=? AND status='SENT' AND valid_until > now()`，
影响行数为 0 就是被抢先了，返回明确错误。**绝不能先查后写。**

### 接受瞬间的原子动作

客户点接受，在**同一事务**内完成：
1. 报价状态 `SENT → ACCEPTED`（带上述条件）
2. 冻结快照（报价内容此后完全不可变，成为合同条款）
3. 生成 `Order` + `OrderLine`（价格、数量、交期从快照复制，不是引用）
4. 生成待下发的 `ProductionOrder` 草稿（基于报价时选定的供应商）
5. 发通知：客户确认函、内部、供应商（待下发提醒）

第 5 步的通知发送要在事务提交**之后**触发，不要在事务内调外部服务。

## 5. 定价引擎

### 计算流程

```
输入：SourcingItem + N 份 SupplierQuoteLine + 目的国 + 数量 + Incoterm + 客户等级
  ↓
① 供应商择优/加权    → 供应商成本(CNY)
② 叠加内部成本项      工装摊销 / 质检 / 包装
③ 叠加物流成本项      国内运费 / 出口费用 / 国际运费（按 applies_to_incoterms 过滤）
④ 叠加税费项          关税 / 清关（同上过滤）
⑤ 汇率换算 + buffer   CNY → EUR
⑥ 叠加毛利           客户等级 × 品类 × 单值档 × 数量档
  ↓
输出：单价(EUR) + 完整 cost_breakdown 快照
```

### 供应商择优 —— MVP 不做算法

D5 定了供应商个位数，**MVP 阶段由采购人工选**，系统只做三件事：
1. 并排展示所有供应商的报价、交期、备注
2. 标出最低价 / 最短交期
3. 展示该供应商的历史表现（合格率、准时率）供参考

**选定后必须记录选择理由**（尤其是没选最低价时）—— 这是将来做算法的训练数据，
也是内部审计需要的。

将来（Phase 5）再做：
`score = w₁·价格 + w₂·交期 + w₃·历史合格率 + w₄·品类经验 + w₅·产能余量`，权重可配。

### 数量阶梯

非标件的数量阶梯不是简单折扣 —— 工装/编程/首件是固定成本，摊到不同数量上单价差异巨大。
所以报价通常要给多个数量档（如 10 / 50 / 100 / 500 件），
**每一档都是一次完整计算**，不是在基准价上打折。

数据结构上：一个 `rfq_item` 可以对应多个 `customer_quote_line`（不同 qty 档）。

## 6. 核心流程时序（下发寻源 + 报价）

```
【后台】RFQ 技术评审通过
   ↓ 检查：每个 rfq_item 的 part_revision 是否有 sanitized 文件？没有 → 按钮禁用
【后台】选择供应商（按能力库筛选）→ 点击「下发寻源」
   ↓ 事务内：
   ① 生成 SourcingPackage（快照 RFQ 的技术信息，脱去所有客户信息）
   ② 生成 SourcingItem（引用 sanitized 文件）
   ③ 为每个选中供应商生成 SupplierInvitation
   ④ 为每份图纸生成带该供应商水印的副本（异步，Phase 2）
   ↓ 事务外：
   ⑤ 发微信 + 邮件通知供应商
   ⑥ 落审计：sourcing.dispatch（含供应商列表、图纸版本、下发人）
【供应商】收到通知 → 手机/PC 登录 → 看到待报价列表
   ↓ 查看图纸（★每次查看落审计 + 短期签名 URL）
   ↓ 填报价（或 Excel 导入）：单价 / 交期 / 有效期 / MOQ / 工装费 / 备注
   ↓ 提交
【后台】收到全部或部分报价 → 并排对比 → 人工选定 + 填选择理由
   ↓ 定价引擎计算 → 生成 CustomerQuote 草稿
   ↓ 提交审批 → 审批通过
   ↓ ★ 校验：所有选定供应商报价的 valid_until ≥ 对客 valid_until
   ↓ 发送给客户
【客户】收到邮件 → 登录看报价 → 点接受
   ↓ 原子转换（见 §4）→ Order 生成
```
