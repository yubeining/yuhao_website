# 14 — 客户入驻与组织账号

> 状态：**方案稿**（2026-11-12）。其中 §2 的四条是需求方当天拍板的，
> 其余是建议方案；**凡是标【待确认】的都没有依据，不许照着实现**。
>
> 编写原因：当前 `/auth/register` 一次就把「人」和「公司」一起建出来，
> 导致一个公司想加第二个采购必须再注册一个公司。这是模型问题，不是表单问题。
>
> **2026-11-12 已落地的第一步（P0）**：注册页删掉「公司名称」，
> 公司照建但名字留空，**提交订单前必须补**。见 §4.4。其余（团队、账单、供应商档案）都还没做。

## 1. 现状与问题

### 1.1 现在是什么样

```java
// IdentityService.register —— 收 RegisterRequest
Organization org = organizations.save(new Organization(orgType, req.orgName(), country));
externalUsers.save(new ExternalUser(org.getId(), email, displayName, passwordHash));
```

注册表单四个字段：**公司名称 / 国家 / 联系人姓名 / 企业邮箱 / 密码** → 一次事务里建公司 + 建人。

### 1.2 由此产生的四个具体问题

| # | 问题 | 表现 |
|---|---|---|
| 1 | **一司多人无法表达** | 同一家公司第二个采购只能再注册一次，于是库里出现两家同名公司，订单、报价、账单各挂一半 |
| 2 | **供应商档案无处安放** | 邀请注册时公司只有一个名字；设备、资质、开票信息没有任何字段可存 |
| 3 | **账单信息没有落点** | VAT 号、账单地址、PO 号在 `organization` 里都没有列 |
| 4 | **「账号」和「客户」混为一谈** | 账号管理页里看到的是人，但业务主体是公司；禁用一个人 ≠ 停用一家公司 |

### 1.3 行业参照（2026-11-12 调研）

| 平台 | 账号模型 | 企业怎么来 |
|---|---|---|
| **webox** | 个人自助注册（邮箱/密码/姓名/手机，**无公司字段**） | 走「联系销售」或凭邀请加入已有企业；企业内有成员审批与角色 |
| **Xometry（买家）** | 个人 Customer Account | 在 dashboard 里建 **Teamspace**（团队空间），邀请同事、分配角色、可共享账单与收货信息；一个账号可开多个 Teamspace |
| **Xometry（供应商）** | 企业账号 | **提交企业信息 → 审核通过才创建账号** → 免费试制件（有体系证书可免）→ 5 单准时保质升为 Trusted Partner |

共同的形态：**「人」先有账号，「公司」是另一个实体；一个公司下有多个人和角色，
账单/资质是公司级信息，按需才收集。**

## 3. 目标模型：人在前，公司在后

```
external_user（人）          organization（公司）
   id / email / 密码            id / type / name / country
   org_id  ───────────────▶     status
   role（新增）                  ├─ 档案（按块存）
                                 ├─ 账单信息
                                 ├─ 资质文件
                                 └─ 分级（供应商）
```

两条硬规矩（沿用 CLAUDE.md §3）：

- **人只能属于一个公司**（`external_user.org_id` 单值）——
  一个人同时是两家公司的采购，不在本轮范围内
- **公司是业务主体**：订单、报价、合同、发票全挂 `org_id`，不挂 `user_id`

## 4. 买家链路（欧洲客户）—— 渐进式，不设门槛

### 4.1 五步

| 步 | 动作 | 建了什么 | 卡不卡 |
|---|---|---|---|
| ① | 注册：邮箱 + 密码（或验证码） | **只建个人账号**，不建公司 | 不卡 |
| ② | 首次询价：填公司名 + 国家 | 此时才建公司（或加入已有公司） | 不卡（可跳过？→ Q1） |
| ③ | 报价 → 确认价格 | — | 不卡 |
| ④ | 下单 / 开票前：补账单信息 | 公司账单块 | **卡在这里** |
| ⑤ | 邀请同事进同一公司 | 成员 + 角色 | — |

### 4.2 每个字段什么时候收

| 字段 | 注册 | 首次询价 | 开票前 | 说明 |
|---|---|---|---|---|
| 邮箱、密码 | ✅ | | | |
| 联系人姓名 | ✅ | | | |
| 公司名称 | | ✅ | | 建公司的触发点 |
| 国家 | | ✅ | | 影响币种与合规 |
| VAT 号 | | | 【待确认】 | D2 说本轮不做 |
| 账单地址 | | | ✅ | 开票必须有 |
| PO 号（采购订单号） | | | 可选 | 客户内部流程要，非必填 |

### 4.3 公司信息的最小集

建公司时**只要求名称 + 国家**。理由：

- 名称是唯一能立刻判定「是不是同一家公司」的字段（配合国家）
- 其余字段（地址、税号、联系人）在开票前补齐即可，提前要只会劝退

> ★ 同名公司：名称 + 国家相同是否就合并为一家？
> 这是**【待确认】Q2** —— 合并错了等于把两家公司的订单搅在一起，比重复建一家危险得多。

### 4.4 已实现的部分（2026-11-12）

与上面 §4.1–4.3 的差别：**公司名补得比原计划更晚** —— 原计划是「首次询价时补」，
实际落在「**提交订单前必须补**」。原因是首次询价那一刻还没有订单，硬卡会让第一次体验变差；
而提交订单已经是不可逆的对外动作，必须有主体。

| 项 | 状态 |
|---|---|
| 注册页去掉「公司名称」 | ✅ 已实现（国家保留，仍写进 `organization.country`） |
| 注册接口 `orgName` 改为可选 | ✅ 已实现；不传则 `organization.name = NULL` |
| `organization.name` 改为可空 | ✅ 迁移 `2026-11-12_01_organization-name-optional.sql` |
| 补公司名入口 | ✅ 「设置 → 公司信息」（仅客户端） |
| 提交订单门禁 | ✅ `submit()` 里校验，未补 → 400 `organization.name_required` |
| 一家公司多人 / 邀请 / 角色 | ❌ 未做（P1） |
| 账单信息 / VAT | ❌ 未做（P2，VAT 按 D2 暂缓） |

**为什么没把 `org_id` 改成可空**：受众（客户/供应商）由 `organization.type` 推出，
租户 id 也来自 org。没有 org 就既不知道这个人属于哪一端，也拿不到 `partyId` —— 连 token 都签不出来。
保留 org、只让名字可空，模型不用动，15 处 `@CurrentParty` 也不用改。

**留白是显式的**：`name = NULL` 表示「还没填」，不是填了个占位符。
运营在账号管理页会看到空公司名，那就是「待完善」的信号。

## 5. 供应商链路（中国工厂）—— 邀请制 + 档案 + 审核 + 分级

### 5.1 五步

| 步 | 动作 | 状态 |
|---|---|---|
| ① | 运营发邀请（已有 `/ops/supplier-invites`） | ✅ 已实现 |
| ② | 凭邀请注册 → 建「联系人 + 公司骨架」 | ✅ 已实现 |
| ③ | 填入驻档案（四块，可存草稿） | ❌ 未实现 |
| ④ | 运营审核 → 通过后才可接单 | ❌ 未实现 |
| ⑤ | 分级：新供应商 / 可信供应商 | ❌ 未实现 |

### 5.2 档案四块（对齐 Xometry 的结构，字段按我们的业务裁剪）

| 块 | 内容 | 用途 |
|---|---|---|
| **A. 加工能力** | 工艺、材料、尺寸范围、精度等级 | 派单时判断能不能做 |
| **B. 设备与资质** | 设备清单（类型/数量/尺寸/精度）、体系证书、检测设备 | 考察依据 |
| **C. 财务与开票** | 营业执照名称（须与公司名一致）、开票信息、银行账户 | 付款、开票 |
| **D. 联系人** | 主联系人 + 其他成员 + 角色 | 派单通知发给谁 |

> 现在 `supplier_profile` 只有 4 个自由文本字段（processes / materials / size_range /
> precision_grade），**B、C、D 三块没有任何落点**。

### 5.3 分级（D4 已确认要做，规则未定）

建议的两级，**判定标准待定**：

| 级别 | 能接什么单 |
|---|---|
| 新供应商 | 只能接小额/试单 |
| 可信供应商 | 可接全部，可能有更优账期 |

判定依据的候选（**都需要你选一个，不要我替你选**）：

- 按**完成单数**（如准时保质完成 5 单）
- 按**人工评定**（运营看过现场/资料后手动设置）
- 按**金额/品类**（如能做的工艺范围）

> 本平台供应商是个位数，我倾向「人工评定」——自动升级在个位数供应商上没有意义，
> 反而多一套状态机要维护。但这是建议，不是决定。

## 6. 付款（D3：待定）

现实里两种都存在：**先款后货**、**先货后款**。平台侧只做两件事：

1. **记录约定的付款条件**（挂在订单上：`payment_terms`）
2. **记录状态流水**（客户已付 / 供应商已收），不收款、不清分

沿用文档 1 的既有决定：**「账款线下走，平台只记录状态」不变。**

需要落的数据挂点（建议）：

```
customer_order.payment_terms   -- PREPAID | NET_XX | 其他，取值待定
payment_event                  -- 谁、何时、哪张单、金额、方式
```

**【待确认】Q3–Q5**：条件有哪几种取值、谁录入、是否影响发货/放单。

## 7. 数据模型建议

### 7.1 新增 / 扩展

| 表 | 动作 | 说明 |
|---|---|---|
| `external_user` | 加 `role` | ADMIN / BUYER / ENGINEER，**【待确认】Q6：角色取值** |
| `organization` | 扩列 | 现有 name/country/status 不动，其余进下面两张表 |
| `company_profile`（新） | 分块存 | `org_id + kind(A/B) + payload(jsonb) + status`，便于逐块审核 |
| `company_billing`（新） | 账单块 | `org_id + 账单地址 + VAT + PO 默认值`（VAT 字段先留，按 D2 不填） |
| `member_invite`（新） | 成员邀请 | 邮箱、角色、过期、状态 —— 现在只有供应商邀请 |
| `supplier_tier`（新或并入 `supplier_profile`） | 分级 | 级别 + 设定人 + 设定时间 + 依据说明 |
| `document`（或复用现有 part_file 那套存储） | 资质文件 | 挂 `org_id + 类型`，走同一套存储与访问审计 |

> **不建外键、关联用裸 uuid、必须显式建索引** —— 沿用 CLAUDE.md §4。

### 7.2 迁移影响

- 现有 `organization` 里只有测试与演示数据，**可以直接改模型**，不必做扩展-收缩
- 注册接口收敛：`/auth/register` 不再收 `orgName` → 公司改为按需创建
- `AccountAdminService` 的「新建外部用户」必须同时接受「新建公司」或「选已有公司」

## 9. 分期

| 期 | 内容 | 前置 | 价值 |
|---|---|---|---|
| **P0** | 注册不建公司；首次询价时建公司（名称+国家） | 无 | 打断「人=公司」的焊死，一司多人才可能 |
| **P1** | 成员邀请 + 角色 + 团队页 | P0 | 多同事协作；账号管理页可扩展 |
| **P2** | 账单信息 + 开票前校验 | P0 | 欧洲 B2B 能开票（VAT 按 D2 暂不做） |
| **P3** | 供应商四块档案 + 审核门 + 分级 | P0 | 供应商准入做实 |

**P0 是地基**：不做 P0，后面全是在错模型上打补丁；而 P0 的改动面最小（注册接口 + 一个创建端点）。
