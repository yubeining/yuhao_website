# 1 — 业务理解与关键决策

> ⚠ **本文档的 §2 链路⑤⑥、D2、D5 已被 [文档 6](./6-供应商派单模式变更.md)（2026-08-14）修订。**
> 供应商侧改为「我们定目标价 → 派单 → 供应商接受/拒绝」，不再收集多家报价综合定价。
> 本文档保留原样作为决策历史，实际以文档 6 为准。

## 1. 我们是什么角色

**接单方 + 集成方**，不是制造方，也不是电商。核心价值在三件事：

1. 把欧洲客户的图纸翻译成中国供应链能报的价
2. 把分散的供应商产能组织成可交付的订单
3. 用质检和物流兜住质量与交期风险

客户买的不是"零件"，是"不用自己去中国找工厂、不用自己管质量和物流"。
所以系统要卖的体验是：**上传图纸 → 拿到确定的价格和交期 → 东西按时送到手上**。

## 2. 完整业务链路

```
① 获客        欧洲客户 Google 搜索 → 官网 → Request a Quote
② 询价        客户注册 → 上传图纸(STEP/DWG/PDF) → 填规格 → 提交 RFQ
③ 技术评审    我们后台：可制造性评审、补齐缺失信息、必要时找客户澄清
④ 脱敏下发    生成匿名寻源包 → 下发给 N 家供应商
⑤ 供应商报价  供应商在系统内填报价（成本 CNY）+ 交期 + 备注
⑥ 综合定价    择优/加权 + 各项成本 + 汇率 + 毛利 → 对客一口价(EUR)
⑦ 内部审批    报价发出前必须过审批闸门
⑧ 对客报价    发送给客户，有有效期
⑨ 客户接受    ★ 点接受 = 正式订单成立（法律上是要约承诺）
⑩ 拆生产订单  按供应商拆；同一零件可拆多家
⑪ 生产跟踪    供应商上报进度 / 里程碑
⑫ 到货质检    我们收货 → 质检 → 通过/返修
⑬ 包装发货    打包 → 交第三方物流 → 出口报关
⑭ 国际运输    第三方承运，我们只接收和转发跟踪信息
⑮ 交付关闭    客户签收 → 订单关闭
※ 账款        线下走，平台只记录"已开票/已收款"状态，不收款不清分
```

## 3. 五个决定架构的业务特征

### 3.1 没有 SKU，核心实体是"图纸版本"

每一行都是「一张图纸 + 材料 + 工艺 + 公差 + 表面处理 + 数量 + 交期」。
没有商品目录、没有库存、没有购物车。

**推论**：核心实体是 `PartRevision`（图纸版本），不是 `Product`。
所有报价、订单、生产、质检、发货**全部锚定具体 revision**，绝不锚定"最新版"。

> 制造业最经典的事故：按 Rev B 报的价，按 Rev C 生产。
> 系统必须让"图纸改版"触发一次显式的"是否重新报价"决策，不能静默继承。

### 3.2 图纸是知识产权，双向信息隔离是硬需求

| 泄露方向 | 后果 |
|---|---|
| 客户图纸 → 同行 | 法律责任，客户流失 |
| 客户身份 → 供应商 | 供应商绕过我们直接接单 |
| 供应商身份 → 客户 | 客户绕过我们直接下单 |
| 对客价 → 供应商 | 供应商知道我们的毛利，下次涨价 |

供应商是个位数、长期合作，做到"绝对匿名"不现实（他们可能已经猜到）。
**务实的底线是三条，必须守死：**

1. 图纸标题栏脱敏（客户 logo / 公司名 / 项目代号 / 零件号）
2. 不暴露客户联系方式和收货地址
3. 不暴露对客报价

### 3.3 三端看的是同一批对象的不同投影，且不对称

这是**跟普通多租户 SaaS 最大的不同**。普通 SaaS 里租户 A 和租户 B 的数据行完全不相交；
这里一个 RFQ 同时要被客户、后台、供应商看到，但看到的东西完全不同。

**最危险的做法是"同一个实体 + 按角色过滤字段"** —— 漏一个字段就是泄露。
解法见文档 2 §3：**投影分离**（物理上分成不同的表）。

### 3.4 报价必须能解释

半年后客户问"为什么这次比上次贵 12%"，你得能拉出：
当时的汇率、当时的供应商成本、当时的运费档、当时的毛利率、用的哪个版本的定价规则。

**推论**：定价规则是数据不是代码；报价行必须快照当时的完整分解；
**绝不 join live 配置去渲染历史单据**。

### 3.5 供应商端是最容易做成"没人用"的一端

中国供应商习惯微信、电话、Excel。你强推门户，大概率的结局是他们照旧发微信，
业务员帮他们代录入，系统变成一个双份工作量的负担。

D5 已拍板"强制上系统"，那么系统必须**降低到比微信更省事**：

- 手机可用（车间里就是用手机）
- 微信/企业微信通知，不是站内信
- 报价支持 Excel 模板导入（他们习惯用 Excel 算）
- 一次报价不超过 3 步
- 图纸能在手机上直接看（PDF 预览，不用下载 CAD 软件）

## 4. 已拍板的决策

### D1 — 数据可存亚洲单区
欧洲客户目前没提数据驻留要求，全部部署在一个区（推荐香港或新加坡，兼顾欧洲延迟和中国供应商访问）。

**但代码上必须预留**：存储桶位置、数据库连接、文件 URL 生成全部走配置，
不在业务代码里硬编码区域。将来真有汽车/医疗客户要求数据不出欧盟时，
才有可能在不重写业务代码的前提下拆出欧洲区。

### D2 — 客户点接受 = 正式订单 ★风险最高的决策
报价在法律上是**要约**，客户接受即合同成立。这意味着：

- 报价发出后汇率涨了 → 我们承担
- 供应商说做不了 → 我们承担
- 报价算错了 → 我们承担

**必须配五道护栏**（详见文档 3 §4）：
① 报价强制有效期 ② 发出前内部审批 ③ 供应商报价有效期必须覆盖对客报价有效期
④ 汇率快照 + buffer ⑤ 客户接受前可撤回且留痕

### D3 — 同一零件可能拆多家供应商
数据模型必须支持 `订单行 → 多个生产订单`。

**核心不变式**：`某订单行分配给各供应商的数量之和 = 该订单行总数量`。
这条要同时写成 DB 约束、Service 校验、集成测试。

> ★ **【已拍板】2026-09-10：`≤` 改成 `=` —— 必须一次派完。**
> 一行零件要么不派，要么把数量全部派出去（可以分给多家，但加起来必须等于总数）。
> 由此**不存在"未分配数量"这个状态**，原先要求的「未分配数量视图」不再需要
> （原文说"否则采购会漏分" —— 现在是从源头上不允许漏分的状态存在）。
> 代价：凑不齐供应商时这一行整个派不出去，卡在待派单。

**QC 按拆分粒度判**：不同供应商做的同一零件，质量是分开判的，
所以质检单挂在"生产订单明细"上，不是挂在订单行上。发货可以合并。

### D4 — 对客先只看一口价
报价单展示给客户的是总价。但**内部必须存全量分解快照**
（供应商成本 / 各项费用 / 汇率 / 毛利率 / 规则版本），
否则半年后无法解释价格，也无法做毛利分析。

将来若要对某些客户开放分项展示，只是前端多渲染几行，数据早就在了。

### D5 — 供应商个位数，强制上系统
- **邀请制开户**，不做自助注册
- **不做招投标机制、不做评分算法**（个位数供应商，人工判断比算法准）
- 供应商能力库（设备 / 工艺 / 材料 / 尺寸范围）还是要建，用于下发时筛选
- 门户必须极简 + 手机可用 + 微信通知 + Excel 导入（见 §3.5）

### D6 — 返修 / 退货 / 索赔 MVP 不做
订单状态机保持简单。但质检不合格是一定会发生的，所以**质检环节必须有 `FAILED` 分支**，
MVP 阶段流程是「质检不合格 → 标记 → 线下处理 → 人工改状态」，
数据模型上预留 `REWORK` 挂载点，将来接完整流程不用改表。
