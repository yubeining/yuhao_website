# 6 — 供应商派单模式变更

> 变更日期：2026-08-14 ｜ 来源：老板口头决策 ｜ 状态：已拍板，待落地
>
> **本文档修订文档 1 的 D2、D5 和文档 3 的寻源/报价链路。**
> 原文档不改 —— 那些决策记录有历史价值，被取代的部分在本文档逐条标注。

---

## 1. 变更内容

### 原设计

```
供应商报价（多家）──▶ 我们择优 + 加价 ──▶ 对客一口价
```
成本由供应商报价决定，我们在其基础上综合定价。

### 变更后

```
我们内部估成本 ──▶ 定目标价 ──▶ 派给匹配的几家供应商 ──▶ 供应商接受 ──▶ 对客报价
```
**价格由我们先定，供应商决定接不接。**

### 老板给的两条依据

1. **客户侧**：客户看到的应该就是"我们"一个对接方 —— 一个价、一个交期，
   看不到供应商层、看不到有几家在报价。
2. **供应商侧**：现有供应商本身就能满足需求，即使直接指派也能接受，
   不需要靠竞价来发现价格。

## 2. 三个新决策

### D7 — 供应商侧改为"目标价派单 + 接受/拒绝"

`SupplierQuote` 的语义从**报价单**退化为**接单确认**：
我们发出目标价，供应商只回 接受 / 拒绝（可附理由或反报价，但反报价不是主路径）。

**取代**：文档 1 §2 链路的 ⑤⑥ 两步、文档 5 Phase 2 的"多家报价并排对比"。

### D8 — 客户是单一对接方，但客户端保留

客户仍然有自己的门户（提需求、看报价、接受、看订单进度），
但**看到的永远只有我们**：一个价、一个交期、一个责任方。
不展示供应商身份、不展示有几家在报价、不展示拆单情况。

> 这一条其实是 D4（对客只看一口价）和文档 1 §3.2 隔离要求的自然延伸，
> 只是现在被明确成产品原则了。

### D9 — 先锁供应商，再报客户 ★

顺序是 **供应商接单 → 才对客户报价**，不是反过来。

| | 方案甲（采纳） | 方案乙（暂不采纳） |
|---|---|---|
| 顺序 | 供应商先接单，成本锁死后再报客户 | 直接给客户报价，事后再找供应商 |
| 优点 | 不会出现"客户下了单但没人做" | 客户当场拿到报价，体验好（Xometry 模式） |
| 代价 | 客户多等一轮（数小时～1 天） | **没人肯接时我们自己贴钱兜住** |

**为什么先做甲**：方案乙的前提是内部成本估算够准，而这套估算模型目前还没经过真实订单校验。
先用甲跑几十单，把"我们估的价 vs 供应商实际接受的价"的偏差摸清楚，
偏差稳定后再切乙 —— **切换成本很低**，状态机顺序调整而已，数据模型不用动。

## 3. 由此产生的四件必须做的事

### 3.1 ★ 新增内部成本估算模块（原设计里没有）

这是本次变更最大的新增工作量。以前供应商报价锚定了我们的成本，
现在**必须在不知道供应商成本的前提下先把价格算出来**。

需要的东西：材料成本、工时估算、复杂度评估。

**输入资料已经有了**：`yuhao_software/报价工时测算-信息整理.md`，
以及仅一那套复杂度算法（见 `参考文件/仅一加工平台流程梳理.md` 第 2 步）——
仅一是"人工填复杂度表 → 套公式算分 → 分数决定走哪条核价路径"，
这个思路可以直接借鉴，它正是"平台自己定价"场景下被验证过的做法。

**注意**：估算规则同样要遵守「定价规则是数据不是代码」（文档 3 §2.3），
放进 `pricing_rule` 体系，改系数不发版。

### 3.2 派单超时必须有兜底

原设计没有这条 —— 因为原来是"收集报价"，等多久都不算异常。
现在派单出去没人接，订单会**悬在那儿**，客户还在等。

必须有明确路径：

```
派单 ──▶ 超时无人接 ──┬─▶ 转下一批供应商
                      ├─▶ 人工指派
                      └─▶ 调整目标价后重派
```

仅一的做法是 24 小时无人接单退回需求方改价重派，可以参考这个时限。

### 3.3 ★ 接单是并发的，必须有数据库层的唯一性保证

多家供应商同时收到派单通知，**接单时间点会撞** —— 哪怕只有 3 家。
不能靠应用层判断"还没人接就让他接"，必须：

- DB 层唯一约束或 `SELECT ... FOR UPDATE` 行锁兜底
- 集成测试必须有并发接单的 case（两家同时接，只能一家成功）

这条和文档 3 §2.4 拆单不变式的三层守护是同一类问题，按同样方式处理。

### 3.4 目标价对供应商也是要约

供应商一点"接受"就成立了。所以**目标价也要有有效期和快照**，
不能只在对客报价侧做护栏。

原来文档 3 §4 护栏③是「供应商报价有效期必须覆盖对客报价有效期」，
现在变成 **「供应商接单承诺的有效期必须覆盖对客报价有效期」** —— 方向反了，要求不变。

## 4. 对 D2 和路线图的影响

### D2（客户点接受 = 正式订单）风险降低了

方案甲下，对客报价发出时供应商已经接单、成本已锁死，
D2 里列的"供应商说做不了 → 我们承担"这条风险基本消除。
**五道护栏仍然全部保留**（汇率、有效期、审批、撤回留痕照旧）。

> 如果将来切换到方案乙，D2 的风险会显著上升，**切换前必须重新评估五道护栏是否够用**。

### 路线图基本不用改

有人会担心"方案甲下供应商接单在对客报价的关键路径上，是不是供应商端要提前到 Phase 1"。
**不用。** Phase 1 阶段业务员用微信问供应商"这个价接不接"，
后台代录"已接受"即可 —— 和原计划"手工录入供应商报价"的工作量一样。

Phase 2 供应商端上线后，把这一步搬到线上，流程不变。

**唯一需要在 Phase 1 就做掉的新东西是 §3.1 的成本估算模块** ——
因为没有它就报不出价，这是新的硬骨头，要加进 Phase 1 的清单。
