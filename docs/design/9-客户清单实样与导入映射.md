# 9 — 客户清单实样与导入映射

> 对象：所有人
> 一句话：拿到第一份真实客户清单之后，逐列核对出来的字段映射与导入规则。
> **本文档的每一条结论都可以在样本文件上复算**，不是推演。
>
> ★ 本文档修订 [文档 7](./7-零件清单与解析.md) §2.1 的必填字段集 —— 那一版
> 假设客户会给图纸版本和材料，实样证明不会。冲突处以本文档为准。

---

## 1. 样本

| | |
|---|---|
| 来源 | 一份已签的暂定价合同，含清单、外协合同、图纸三维 |
| 位置 | `参考文件/江苏昱昊机械有限公司  -暂定价合同64062/` |
| 清单 | 58 个数据行，57 个不同图号，总价 64062.85 |
| 图纸 | 21 个批次目录，197 个文件 |

**校验过**：58 行小计相加 = 合同总价，误差 0；每一行 `数量 × 单价 = 小计`，无例外。
所以这份清单的数字是自洽的，可以当基准用。

## 2. 实样有哪些列

清单只有 A–K 十一列，没有隐藏列。

| 列 | 表头 | 含义 | 判定依据 |
|---|---|---|---|
| A | 序号 | 行号 1–58 | 连续无跳号 |
| B | 任务编号 | **委托方的批次号** | 21 个不同值，**与 21 个图纸目录一一对应** |
| C | 系统号 | 装在哪台整机 | 14 个值，粒度大于图号 |
| D | 课题号 | 项目归属，比系统号高一层 | 16 个值 |
| E | 图号 | **零件唯一标识** | 57 个值，`LB` + 三段数字 |
| F | 名称 | 中文名 | |
| G | 数量 | 件数 | |
| H | 含税单价 | 元/件 | |
| I | 含税总价 | = G × H | 全部行校验通过 |
| J | *无表头* | **这一行怎么消化** | 取值：有合同 44 / 有合同（经手人）6 / 装配 4 / 自制 3 / 采购 1 |
| K | *无表头* | **承接方** | 只有 6 行填了，52 行空 |

第 60 行是合并单元格 `A60:H60`，写总价。**文件名末尾的数字就是总价。**

### 2.1 三个编号是三个粒度，别混

```
课题号  ── 委托方的项目
  └ 系统号 ── 装在哪台整机上
      └ 图号 ── 具体零件
任务编号 ── 我方批次，和上面三个正交
```

**系统号和课题号是零件的固有属性。**57 个图号里 56 个恒定对应同一组
（系统号，课题号）；唯一的例外只是分属两个批次，系统号课题号完全一样。

**任务编号不是零件属性。**同一个图号可以出现在两个批次里（样本里有一例）。

这决定了它们各自该落在哪张表 —— 见 §5。

## 3. 实样缺什么（本文档存在的理由）

**清单里没有材料，没有表面处理，没有图纸版本。**

文档 7 §2.1 把「图纸版本」列为 **不允许为空、空即退回客户**，把「材料」列为必填。
按那一版规则，**这份真实清单一行都进不来**。

### 3.1 图纸版本的真实来源：文件名，不是清单

图纸文件名里带版本号：

```
模型_4_1_LB8.605.63529_A_(密级为空)_860563529.par
                       ↑ 版本
```

样本里版本 A 出现 69 次、B 10 次、C 2 次。**每个图号只有一个版本**，
所以这批数据不存在同图号多版本的歧义 —— 但这是样本的偶然，不能当规律。

### 3.2 材料与表面处理：清单和文件名里都没有

只可能在图纸内容里（PDF 图框 / 技术要求栏）。
**平台拿不到，除非有人看图。**

## 4. 导入规则

### 4.1 三类字段，三种来源

| 类 | 字段 | 来源 | 缺失时 |
|---|---|---|---|
| **必填** | 图号、名称、数量 | 清单，实样全有 | 该行**不能导入**，退回 |
| **可从图纸推导** | 图纸版本 | 图纸文件名 | 进「待确认」，不阻断导入 |
| **只能人工补** | 材料、表面处理 | 看图或问客户 | 进「待确认」，不阻断导入 |
| **原样存** | 任务编号、系统号、课题号 | 清单 | 空着即可 |

### 4.2 ★ 导入不拦截，报价才拦截

**这是本文档最重要的一条，也是对文档 7 的主要修订。**

文档 7 的做法是导入时就卡住不合格的行。实样证明这条走不通 ——
客户给的清单天然缺三个字段，卡住的结果是一行都进不来，客户会直接放弃。

**改成两道闸门：**

```
导入  ── 只要图号 / 名称 / 数量齐全就收进来，缺的字段标「待确认」
                              ↓
补齐  ── 版本从文件名解析；材料和表面处理由我方看图填
                              ↓
确认  ── 补出来的值必须客户点头（我方填的不能算数）
                              ↓
报价  ── 只有全部确认过的行才进报价
```

**为什么补齐的值必须客户确认**：材料是定价的直接输入。我方看图看错一个牌号，
报出去的价就是错的，而客户从报价单上看不出这个数是谁定的。
让他确认一次，责任边界才清楚。

### 4.3 图纸与清单行的匹配

文档 7 §6 假设文件名是「零件号 + 版本」。**实样的命名有五种风格：**

| 风格 | 数量 | 例 |
|---|---|---|
| `模型_…_图号_版本_(密级)_数字ID` | 56 | `模型_4_1_LB8.605.63529_A_(密级为空)_860563529.par` |
| 纯数字 ID | 51 | `835460372.par` |
| `图号紧凑写法-中文名` | 38 | `LB860062384-垫圈.pdf` |
| `A3_dft_…_图号_版本_(密级)_…_print` | 31 | `A2_dft_7_1_LB8.034.60696_A_(非密)_803460696_print.pdf` |
| 无规律 | 9 | `GB9074'8_3X8.prt` |

**数字 ID 就是图号去掉 `LB` 和小数点**：`860563529` ↔ `LB8.605.63529`。
所以纯数字命名的文件也能还原图号 —— 但这个规则是从样本反推的，**只在这个客户身上验证过**。

**做法**：

1. 先按目录归集 —— 文件在哪个批次目录下，就属于哪个任务编号
2. 目录内按图号匹配到具体行，支持上面几种写法 + 数字 ID 还原
3. 匹配不上的，在确认界面手工拖拽关联
4. **命名规则按客户记忆**（同文档 7 §4.2 的列映射记忆），
   第二次导入直接复用，不要每次重猜

## 5. 落库

零件相关的表已经存在（`part` / `part_revision` / `part_file`），
本次只补客户的三个参考编号。

```sql
-- 系统号 / 课题号：零件固有属性
ALTER TABLE part ADD COLUMN IF NOT EXISTS customer_system_no text;
ALTER TABLE part ADD COLUMN IF NOT EXISTS customer_topic_no  text;

-- 任务编号：批次，不是零件属性
ALTER TABLE rfq_item ADD COLUMN IF NOT EXISTS customer_task_no text;

-- 客户拿这三个编号反查是最高频路径，必须显式建索引
-- （无外键 = 没人替你建，见 CLAUDE.md §4）
CREATE INDEX IF NOT EXISTS idx_part_customer_system_no
    ON part (customer_party_id, customer_system_no)
    WHERE customer_system_no IS NOT NULL;
CREATE INDEX IF NOT EXISTS idx_part_customer_topic_no
    ON part (customer_party_id, customer_topic_no)
    WHERE customer_topic_no IS NOT NULL;
CREATE INDEX IF NOT EXISTS idx_rfq_item_customer_task_no
    ON rfq_item (customer_task_no)
    WHERE customer_task_no IS NOT NULL;
```

**三列全部可空、不加唯一约束、不做格式校验。**
编号规则是客户定的，换个客户就变。任何「必须几位」「必须唯一」的假设
都会在第二个客户那里炸。我方一个字都不用它们计算 —— 存它们唯一的理由是
客户要拿我方单据回去对他自己的账。

### 5.1 完整映射

| 清单列 | 落在哪 | 状态 |
|---|---|---|
| A 序号 | `rfq_item.line_no` | 已有 |
| B 任务编号 | `rfq_item.customer_task_no` | 本次加 |
| C 系统号 | `part.customer_system_no` | 本次加 |
| D 课题号 | `part.customer_topic_no` | 本次加 |
| E 图号 | `part.customer_part_no` | 已有 |
| F 名称 | `part.name` | 已有 |
| G 数量 | `rfq_item.qty` | 已有 |
| H 含税单价 | 报价行，**我方算，客户不填** | 已有 |
| I 含税总价 | 算出来的，不存 | — |
| J 生产方式 | 由派单结果推导 | 派单表已有 |
| K 承接方 | 抢单成功时自动写 | 派单表已有 |
| — 图纸版本 | `part_revision.rev_code`，从文件名解析 | 已有列，来源本文档补 |
| — 材料 | `part_revision.material`，人工补 + 客户确认 | 同上 |
| — 表面处理 | `part_revision.surface_treatment` | 同上 |

## 6. 实样暴露的两个业务问题

**一、J 列说「有合同」的 50 行里，44 行的 K 列（承接方）是空的。**
手工台账必然如此。系统化之后承接方是抢单那一刻自动写的，不会漏 ——
这条正是平台相对 Excel 的直接价值，值得拿这份样本给客户看。

**二、这一张表同时在干四件事**：报价单、零件清单、外协台账、图纸索引。
平台把它拆成「询价 → 报价 → 订单 → 派单包」四个对象。
迁移时要让客户认得出对应关系，否则他会觉得变复杂了。
